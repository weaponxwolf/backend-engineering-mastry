# Backend Interview Answers

In senior engineering interviews, reciting textbook definitions will get you rejected. Interviewers look for **structural clarity, deep mechanical understanding of underlying systems, awareness of production failure modes, and clear articulation of engineering tradeoffs**.

<Tip>
Use the **Senior Answer Formula**:
1. **Core Mechanism**: How the component physically operates under the hood.
2. **Failure Mode / The Trap**: The edge case or pitfall where naive code breaks.
3. **Production War Story**: A concrete example from real systems (PostgreSQL, Java 21, Linux, or HTTP).
</Tip>

## 0. Non-Negotiable Backend Fundamentals

<AccordionGroup>
  <Accordion title="1. What physically is a backend?">
    A backend is a long-running operating system process behind a network boundary. The JVM process starts, Spring Boot creates controllers/services/repositories, embedded Tomcat binds a server socket to a port such as `8080`, and Linux accepts TCP connections for that socket. The framework is helpful, but the physical pieces are process, memory, threads, sockets, HTTP bytes, durable state, and response bytes.
  </Accordion>

  <Accordion title="2. Why should a controller stay thin?">
    A controller is an HTTP adapter. It should translate path variables, query parameters, headers, and JSON bodies into a typed use-case call. Business rules belong in services because services can own transaction boundaries, authorization decisions, domain invariants, and orchestration. A controller that directly writes repositories usually spreads business logic across endpoints and makes security harder to prove.
  </Accordion>

  <Accordion title="3. Why must the backend never trust the client?">
    The client controls the bytes outside your server. A browser, mobile app, proxy, or script can forge `userId`, `role`, `priceCents`, `discount`, and path IDs. The backend must load authoritative state from the database, derive identity from the authenticated security context, calculate prices server-side, and scope repository queries by ownership.
  </Accordion>

  <Accordion title="4. Why are DTOs separate from JPA entities?">
    Request DTOs model client intent. Entities model persisted domain state. Response DTOs model public API contract. Returning or accepting entities directly can cause mass assignment, password/hash leaks, lazy-loading during serialization, infinite recursion, API contract drift when tables change, and accidental persistence of fields the client should never control.
  </Accordion>

  <Accordion title="5. What is idempotency and why does it matter?">
    Networks fail after the server commits but before the client receives the response. If the client retries `POST /orders`, the server may create duplicate orders. An idempotency key stores the caller's operation identity, usually enforced with a unique database constraint per user, so repeated attempts return the original result instead of repeating the side effect.
  </Accordion>

  <Accordion title="6. What is the basic transaction answer that is not shallow?">
    A transaction is an atomic unit of database work, but the senior answer must include isolation and concurrency. Two transactions can still race, read stale snapshots, lose updates, or create write skew depending on isolation level and query shape. Protect invariants with atomic SQL updates, row locks, optimistic versions, unique constraints, and tests that run concurrent attempts.
  </Accordion>

  <Accordion title="7. What does Docker actually do?">
    Docker starts a normal Linux process from an image. The image is a layered read-only filesystem plus metadata. The running container uses Linux namespaces for isolation and cgroups for CPU and memory enforcement. It is not a VM. `localhost` inside the container means the container's own network namespace.
  </Accordion>

  <Accordion title="8. What does Kubernetes actually do?">
    Kubernetes is a reconciliation system. You declare desired state, such as 3 replicas of `notes-api`, and controllers continuously work to match reality to that state. Pods run containers, Deployments manage rolling updates, Services provide stable networking over changing pod IPs, readiness removes unsafe pods from traffic, and liveness restarts stuck processes.
  </Accordion>

  <Accordion title="9. What is the difference between logs, metrics, and traces?">
    Metrics show system health over time, such as rate, errors, duration, and saturation. Traces show where one request spent time across services. Logs show detailed contextual events and exceptions. Production debugging usually starts from a metric alert, jumps to an exemplar or trace, then opens correlated logs using the same trace ID.
  </Accordion>

  <Accordion title="10. What does every good backend answer end with?">
    A proof test. If you claim ownership is enforced, show a test where User A cannot read User B's row. If you claim idempotency works, send the same key twice and prove one row exists. If you claim a cache is safe, test stale refill and tenant isolation. If you claim Kubernetes rollout is safe, run a rollout under traffic.
  </Accordion>
</AccordionGroup>

## 1. Networking & Socket Layer Internals

<AccordionGroup>
  <Accordion title="1. Walk through an API call end-to-end (POST https://api.store.com/v1/orders)">
    - **Step 1: DNS Resolution**:
      - The browser/client checks local DNS cache, OS resolver cache, and queries the local recursive DNS server.
      - If uncached, the recursive resolver queries Root (`.`), TLD (`.com`), and Authoritative DNS servers (using Anycast BGP routing) to resolve `api.store.com` to an IPv4/IPv6 address.
    - **Step 2: TCP 3-Way Handshake**:
      - Client sends `SYN` (packet with random Initial Sequence Number $ISN_c$).
      - Server responds with `SYN-ACK` (acknowledges $ISN_c + 1$ and sends server $ISN_s$).
      - Client sends `ACK` (acknowledges $ISN_s + 1$). The connection is now established.
    - **Step 3: TLS 1.3 Cryptographic Handshake (1-RTT)**:
      - Client sends `ClientHello` with supported cipher suites, key shares (ECDHE), and ALPN (`h2, http/1.1`).
      - Server sends `ServerHello` with selected cipher, server key share, certificate chain, and finished message. Both compute the symmetric master encryption key in 1 Round-Trip Time (1-RTT).
    - **Step 4: HTTP Request & Edge Routing**:
      - Client encrypts and transmits the HTTP/2 frame: `POST /v1/orders` with headers and JSON body.
      - AWS ALB / NGINX Reverse Proxy terminates TLS, validates standard headers, and forwards over internal Keep-Alive TCP connections to an available Spring Boot instance.
    - **Step 5: Spring Boot Processing**:
      - Tomcat assigns the request to an OS/Virtual worker thread.
      - Spring Security filter chain validates the JWT `Authorization` header.
      - `DispatcherServlet` maps the URI to `OrderController.createOrder()`.
      - Jackson deserializes JSON bytes into a Java 21 Record `CreateOrderRequest`.
      - The service executes inside a `@Transactional` boundary, checks out a HikariCP database connection, executes SQL against PostgreSQL, and commits.
    - **Step 6: Response Flow**:
      - The controller returns `201 Created` with a `Location: /v1/orders/ORD-9821` header.
      - Jackson serializes the response entity to JSON and flushes bytes back through the socket.
  </Accordion>

  <Accordion title="2. Explain the TCP 4-way termination, TIME_WAIT state, and socket exhaustion">
    - **The Mechanism**:
      - When an HTTP connection closes, TCP executes a 4-way termination:
        1. Initiator sends `FIN` (Active Close).
        2. Receiver sends `ACK`.
        3. Receiver finishes sending remaining data and sends its own `FIN`.
        4. Initiator sends `ACK` and enters the **`TIME_WAIT`** state.
    - **Why `TIME_WAIT` Exists**:
      - The socket stays in `TIME_WAIT` for $2 \times \text{MSL}$ (Maximum Segment Lifetime, typically 60 seconds) to ensure the final `ACK` is received by the peer and to ensure delayed packets from old connections expire without corrupting future connections reusing the same 4-tuple `(src_ip, src_port, dst_ip, dst_port)`.
    - **The Production Disaster (Ephemeral Port Starvation)**:
      - If a microservice creates a new `HttpClient` or `RestTemplate` for every downstream call without connection pooling, it opens and closes thousands of TCP sockets per second.
      - All ephemeral ports ($32768\text{--}60999 \approx 28,000$ ports) get trapped in `TIME_WAIT`.
      - Subsequent calls crash with: `java.net.NoRouteToHostException: Cannot assign requested address`.
    - **The Solution**:
      1. Always pool HTTP connections using Apache HttpClient 5 or pooled `RestClient` (`keep-alive` connection reuse).
      2. Enable Linux kernel socket reuse: `sysctl -w net.ipv4.tcp_tw_reuse=1`.
  </Accordion>

  <Accordion title="3. Compare HTTP/1.1 vs HTTP/2 vs HTTP/3">
    - **HTTP/1.1**:
      - Text-based protocol. Supports persistent connections (`Connection: keep-alive`), but suffers from **Application-Layer Head-of-Line (HoL) Blocking**: only one request can be processed per TCP connection at a time. Browsers open 6 parallel TCP connections per domain to compensate.
    - **HTTP/2**:
      - Binary framing layer. Introduces bidirectional **multiplexed streams** over a single TCP connection. Multiple requests and responses interleave concurrently without waiting for previous requests to finish.
      - **The Hidden Flaw**: HTTP/2 still runs on TCP. If a single TCP packet is dropped on a lossy cellular network, the entire TCP connection stalls (TCP Head-of-Line Blocking) while the kernel waits for retransmission, blocking all multiplexed streams.
    - **HTTP/3**:
      - Replaces TCP with **QUIC over UDP**. Each stream has independent packet recovery. If packet 3 in Stream A is lost, Stream B continues processing with zero latency stalls. Handshake is reduced to 0-RTT/1-RTT with built-in TLS 1.3 encryption.
  </Accordion>

  <Accordion title="4. Differentiate Connection Timeout vs Read Timeout vs Socket Timeout">
    - **Connection Timeout**:
      - Maximum time allowed to establish the initial TCP 3-way handshake with the target host.
      - If the remote server is down, firewall drops the `SYN` packet, or network route fails, it throws `java.net.ConnectException: Connection refused` or `ConnectTimeoutException`.
      - **Production Value**: Should be short (e.g., 500ms to 2000ms).
    - **Read Timeout (Socket Timeout / `SO_TIMEOUT`)**:
      - Maximum time allowed between two consecutive data packets arriving on an established socket.
      - It is **not** a timeout for the entire request duration; it is an inactivity timer. If the server accepts the connection but takes 30 seconds to compute a database query before sending the first byte, a 5-second Read Timeout throws `java.net.SocketTimeoutException: Read timed out`.
      - **Production Value**: Set based on downstream p99 SLA (e.g., 3000ms to 5000ms).
    - **Execution Timeout**:
      - End-to-end deadline managed at the application layer (e.g., Resilience4j `TimeLimiter` or gRPC Deadlines) encompassing connection, request transmission, and full response reading.
  </Accordion>

  <Accordion title="5. How does TCP apply backpressure across socket buffers?">
    - Every TCP socket has a kernel send buffer (`SO_SNDBUF`) and receive buffer (`SO_RCVBUF`).
    - The receiver advertises its available receive buffer space in the **Receive Window (`win`)** field of every TCP header.
    - When a fast producer sends data faster than a slow consumer reads from its socket, the consumer's `SO_RCVBUF` fills up.
    - The consumer's kernel reduces the advertised window size to 0 (**Zero Window**).
    - The producer's kernel stops transmitting packets and buffers unsent data in `SO_SNDBUF`.
    - Once `SO_SNDBUF` fills, the producer's application-layer `socket.write()` or Java `OutputStream.write()` call **blocks** the calling thread.
    - This is mechanical backpressure: slow consumers automatically throttle fast producers without any custom application messaging.
  </Accordion>
</AccordionGroup>

## 2. Core Java & JVM Runtime Internals

<AccordionGroup>
  <Accordion title="1. Trace HashMap.put(K, V) under the hood down to bitwise operations">
    - **Step 1: Hash Spreading (`hash(key)`)**:
      ```java
      static final int hash(Object key) {
          int h;
          return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
      }
      ```
      The 32-bit integer is XORed with its high 16 bits. This ensures high-order bits influence the lower index bits, drastically reducing collisions when table capacity is small.
    - **Step 2: Bucket Index Calculation**:
      - `index = (n - 1) & hash`, where `n` is table capacity.
      - Because capacity `n` is strictly a power of 2 (e.g., 16, 32, 64), `(n - 1)` is a bitmask of all 1s (e.g., $16 - 1 = 15 = \text{00001111}_2$).
      - The bitwise `&` operation is mathematically equivalent to `hash % n`, but executes in a single CPU cycle.
    - **Step 3: Collision Resolution & Treeification**:
      - If the bucket is empty, a `Node<K,V>` is inserted.
      - If occupied, it traverses the singly-linked list checking `p.hash == hash && ((k = p.key) == key || (key != null && key.equals(k)))`.
      - If the list reaches **8 nodes**, `treeifyBin()` is called.
      - **The Guard Clause**: If the total table capacity is less than **64**, the table simply resizes (`resize()`) rather than converting to a tree.
      - If capacity is $\ge 64$, the linked list converts into a **Red-Black Tree** (`TreeNode<K,V>`), transforming search time from $O(N)$ worst-case to $O(\log N)$ to defend against HashDoS algorithmic attacks.
    - **Step 4: Resize at 0.75 Load Factor**:
      - When `size > threshold` (`capacity * 0.75`), capacity doubles.
      - Because capacity doubles by a power of 2, a node either stays at its current index `j` or moves to `j + oldCap`. It checks `(hash & oldCap) == 0`. No re-hashing is required!
  </Accordion>

  <Accordion title="2. What happens if equals() and hashCode() contracts are violated?">
    - **The Contract**:
      1. If `a.equals(b)` is `true`, then `a.hashCode() == b.hashCode()` **must** be `true`.
      2. If `a.hashCode() == b.hashCode()`, `a.equals(b)` may or may not be `true` (hash collision).
    - **Violation 1: Equal objects with different hashCodes**:
      ```java
      class User {
          String email;
          // Implements equals based on email, but forgot to override hashCode()
      }
      ```
      If you insert `new User("alex@test.com")` into a `HashSet`, and later call `set.contains(new User("alex@test.com"))`:
      - The second object produces a different default `System.identityHashCode()`.
      - The JVM looks in the wrong bucket and returns `false`, corrupting set uniqueness!
    - **Violation 2: Mutating key fields in a HashMap (Silent Memory Leak)**:
      ```java
      User user = new User("alex@test.com");
      map.put(user, "SESSION_DATA");
      user.setEmail("alex_updated@test.com"); // Mutated hashCode field!

      map.get(user); // Returns null!
      ```
      When `user.setEmail()` changed the email, its `hashCode()` changed. `map.get()` now computes a new bucket index, where the object does not exist. The original entry is trapped in the old bucket and can **never** be retrieved or removed, causing a silent memory leak.
  </Accordion>

  <Accordion title="3. Explain == vs .equals() and the Integer Cache trap">
    - **`==`**: Compares memory addresses (references) for objects; compares raw binary values for primitives.
    - **`.equals()`**: Compares logical equivalence as defined by the class author.
    - **The Trap**:
      ```java
      Integer a = 100;
      Integer b = 100;
      System.out.println(a == b); // true!

      Integer x = 200;
      Integer y = 200;
      System.out.println(x == y); // false!
      ```
    - **Why**:
      - Java caches `Integer` objects between **-128 and 127** via `Integer.IntegerCache`.
      - When auto-boxing values within this range, `Integer.valueOf()` returns the identical cached object reference.
      - For values $\ge 128$, `Integer.valueOf()` executes `new Integer(i)`, allocating separate heap objects.
    - **Production Impact**: Never compare database entity IDs (`order.getUserId() == currentUser.getId()`) with `==`. If User ID is 42, the code passes in dev; when User ID hits 150 in production, authorization fails intermittently! Always use `.equals()`.
  </Accordion>

  <Accordion title="4. How do Compact Strings in Java 9+ save 50% heap memory?">
    - Prior to Java 9, `String` stored characters as a `char[]` array. Since Java `char` is UTF-16, every character consumed **2 bytes**, even for standard ASCII text where the high byte is always `0x00`.
    - Java 9 introduced **Compact Strings**:
      ```java
      public final class String {
          private final byte[] value;
          private final byte coder; // 0 for LATIN1, 1 for UTF16
      }
      ```
    - If a string contains only ISO-8859-1 / ASCII characters (typical for JSON keys, URLs, emails), `coder` is set to `LATIN1` and characters consume **1 byte** each.
    - In production enterprise web services where strings represent 30% to 50% of heap memory, this single optimization reduced JVM heap footprints by 25% to 40% with zero code changes.
  </Accordion>

  <Accordion title="5. Why is LinkedList an antipattern compared to ArrayList?">
    - Computer science textbooks teach that `LinkedList` has $O(1)$ insertions while `ArrayList` has $O(N)$ worst-case copy overhead. In modern computer architecture, this is wrong.
    - **Hardware Reality (CPU Cache Lines)**:
      - Modern CPUs fetch memory into L1/L2/L3 caches in **64-byte cache lines**.
      - `ArrayList` stores elements in a contiguous memory block. Iterating through an `ArrayList` triggers hardware spatial prefetching, loading sequential elements into L1 cache with near-zero latency (~1ns).
    - **The LinkedList Flaw**:
      - `LinkedList` allocates a `Node` object for every single element (`Node` overhead: 24 bytes of object header and pointers for 4 bytes of payload).
      - Nodes are scattered randomly across the heap. Every step of traversal causes a **CPU cache miss**, forcing the CPU to stall for 50ns to 100ns waiting for main RAM.
    - **Benchmark Reality**: An `ArrayList` is faster than a `LinkedList` for insertion, deletion, and traversal for virtually all realistic data sizes ($N < 100,000$).
  </Accordion>

  <Accordion title="6. What is the Carrier Thread Pinning Trap in Java 21 Virtual Threads?">
    - **The Mechanism**:
      - Java 21 Virtual Threads are user-mode threads managed by the JVM.
      - Thousands of virtual threads are multiplexed over a small pool of OS kernel threads called **Carrier Threads** (`ForkJoinPool`).
      - When a virtual thread executes a non-blocking I/O operation (e.g., reading from a socket), it unmounts from its carrier thread, allowing other virtual threads to run.
    - **The Pinning Trap**:
      - If a virtual thread enters a **`synchronized` block or method**, or calls a native method (JNI), and then performs blocking I/O inside it:
      - The virtual thread **pins** the carrier thread. It cannot unmount.
      - If 50 virtual threads enter `synchronized` methods and wait for database queries, all 50 carrier threads become blocked. The entire carrier pool starves, freezing the application.
    - **The Fix**:
      - Replace `synchronized` with **`ReentrantLock`** when guarding I/O operations. `ReentrantLock` allows the virtual thread to unmount cleanly without pinning carrier threads.
  </Accordion>
</AccordionGroup>

## 3. Database Engine & Relational Storage Internals

<AccordionGroup>
  <Accordion title="1. What is the 11-step Logical Query Processing Order in SQL?">
    - When an SQL query executes, the database engine processes clauses in a strict mathematical order, distinct from the written syntax:
      1. `FROM`: Identify and load target tables.
      2. `ON`: Apply join conditions.
      3. `JOIN`: Physically execute table joins (Nested Loop, Hash Join, Merge Join).
      4. `WHERE`: Filter rows prior to grouping (cannot use window functions or aggregates).
      5. `GROUP BY`: Aggregate rows into distinct buckets.
      6. `HAVING`: Filter grouped buckets (can evaluate aggregate functions).
      7. `WINDOW`: Compute analytical window functions (`ROW_NUMBER()`, `RANK()`, `OVER`).
      8. `SELECT`: Project columns, evaluate expressions, and assign aliases.
      9. `DISTINCT`: Eliminate duplicate projected rows.
      10. `ORDER BY`: Sort the final result set.
      11. `LIMIT / OFFSET`: Discard rows outside the pagination window.
    - **The Senior Insight**:
      - This explains why `SELECT total * 0.1 AS tax FROM orders WHERE tax > 50` crashes with `column "tax" does not exist`. `WHERE` executes at Step 4, while `tax` is only defined at Step 8 (`SELECT`).
  </Accordion>

  <Accordion title="2. Why do databases use B+Trees instead of Binary Search Trees or Hash Indexes?">
    - **Binary Search Tree (BST) Flaw**:
      - A BST has a fanout of 2. For 100,000,000 rows, tree height is $\log_2(100,000,000) \approx 27$.
      - If each node is on a separate disk block, reading a record requires 27 sequential disk I/Os. On a spinning disk (10ms/seek), this takes 270ms. On SSD (100μs), it takes 2.7ms.
    - **Hash Index Flaw**:
      - $O(1)$ lookup for exact match (`WHERE id = 42`), but completely useless for range queries (`WHERE created_at >= '2026-01-01'`) or sorting (`ORDER BY created_at`).
    - **B+Tree Superiority**:
      - **High Fanout**: Nodes match the database page size ($8\text{ KB}$ in Postgres, $16\text{ KB}$ in MySQL). A single node holds 300 to 500 keys.
      - **Shallow Height**: For 50,000,000 rows, a B+Tree with fanout 400 has a height of only 3.
      - Root and branch pages remain permanently cached in RAM buffer pools.
      - Locating any row requires **at most 1 physical disk read**!
      - **Doubly-Linked Leaves**: All leaf nodes are linked sequentially. Range scans (`BETWEEN 10 AND 50`) find the start key in $O(\log N)$ and then iterate linearly along the leaf chain with zero tree re-traversals.
  </Accordion>

  <Accordion title="3. Explain Composite Indexes and the Leftmost Prefix Rule">
    - Suppose you have an index on `(status, created_at, user_id)`.
    - **How It Is Physically Stored**:
      - Data is sorted first by `status`. For rows with identical `status`, sorted by `created_at`. For rows with identical `status` and `created_at`, sorted by `user_id`.
    - **Phonebook Analogy**:
      - A phonebook is sorted by `(LastName, FirstName)`.
      - Searching for `LastName = 'Smith'` is instant.
      - Searching for `LastName = 'Smith' AND FirstName = 'John'` is instant.
      - Searching for `FirstName = 'John'` without a last name forces you to scan the entire phonebook from start to finish.
    - **Query Evaluation**:
      - `WHERE status = 'PAID' AND created_at > ?` $\rightarrow$ **Index Range Scan** (Optimal).
      - `WHERE created_at > ? AND user_id = 42` $\rightarrow$ **Sequential Scan** (Index cannot be used because `status` is skipped).
      - `WHERE status = 'PAID' AND user_id = 42` $\rightarrow$ Uses index on `status`, then checks `user_id` via filter.
  </Accordion>

  <Accordion title="4. How does a Covering Index with INCLUDE enable Index-Only Scans?">
    - **Normal Index Scan**:
      1. Traverse B+Tree to find index entry matching `WHERE user_id = 42`.
      2. Extract the physical tuple pointer (`t_ctid` = Page 12, Item 4).
      3. Read the 8 KB table heap page from disk to retrieve non-indexed columns (`total_amount`).
    - **Covering Index (`INCLUDE`)**:
      ```sql
      CREATE INDEX idx_orders_user_covering 
      ON orders (user_id) INCLUDE (total_amount, status);
      ```
      The B+Tree key is `user_id` (used for tree navigation). The leaf node payload directly stores `total_amount` and `status`.
    - **Index-Only Scan**:
      - When running `SELECT total_amount, status FROM orders WHERE user_id = 42`, the engine extracts all requested columns directly from the B+Tree leaf page.
      - It **never touches the physical table heap** (verified by the PostgreSQL Visibility Map). This eliminates 90%+ of random disk page reads.
  </Accordion>

  <Accordion title="5. Why does UPDATE in PostgreSQL physically perform an INSERT and DELETE?">
    - PostgreSQL uses Multi-Version Concurrency Control (MVCC) without rollback segments (unlike MySQL InnoDB's Undo Log).
    - Every row has a TupleHeader containing:
      - `xmin`: Transaction ID that created the row.
      - `xmax`: Transaction ID that deleted or updated the row (0 if active).
      - `t_ctid`: Physical pointer to the current or newer version of the row.
    - **When you run `UPDATE accounts SET balance = 500 WHERE id = 1`**:
      1. PostgreSQL does not overwrite the existing data in-place.
      2. It sets `xmax = current_tx_id` on the existing row version (marking it dead for future transactions).
      3. It physically **inserts** a brand-new row version on an available 8 KB page with `xmin = current_tx_id` and sets `t_ctid` on the old row pointing to the new row.
    - **Table Bloat & VACUUM**:
      - Dead tuples remain on disk so concurrent running transactions can read older snapshot versions.
      - If `VACUUM` (or `autovacuum`) is delayed or blocked by long-running transactions, dead tuples accumulate, causing **table bloat** and degrading scan performance.
  </Accordion>

  <Accordion title="6. Why must financial balances never use float or double?">
    - **The Binary Rounding Disaster**:
      - Modern CPUs represent `float` and `double` using IEEE 754 floating-point binary format (powers of 2: $1/2, 1/4, 1/8$).
      - Most decimal fractions (like `0.1` or `0.01`—one cent) cannot be represented accurately in binary, resulting in recurring fractions:
      ```java
      System.out.println(0.1 + 0.2); // Prints 0.30000000000000004 !
      ```
    - **The BigDecimal Trap**:
      ```java
      BigDecimal bad = new BigDecimal(0.1); 
      // Prints: 0.1000000000000000055511151231257827021181583404541015625 !

      BigDecimal good = BigDecimal.valueOf(0.1); // Uses Double.toString(0.1)
      // Prints: 0.1
      ```
    - **The Production Standard**:
      1. **Database**: Store money as `NUMERIC(19, 4)` or as integer cents in `BIGINT` (`1000` = $10.00).
      2. **Java**: Store money in integer cents (`long`) or use a rich `Money` record wrapping `BigDecimal` with explicit `RoundingMode.HALF_EVEN` (Banker's Rounding).
  </Accordion>
</AccordionGroup>

## 4. Concurrency, Locking & Transaction Anomalies

<AccordionGroup>
  <Accordion title="1. Explain Write Skew and why Repeatable Read allows it">
    - **The Concurrency Anomalies Spectrum**:
      - **Dirty Read (P1)**: Reading uncommitted data from another transaction.
      - **Non-Repeatable Read (P2)**: Reading the same row twice and getting different values because another transaction committed an update.
      - **Phantom Read (P3)**: Reading a range of rows twice and finding new rows added by another committed transaction.
      - **Write Skew (A5B)**: Two concurrent transactions read overlapping data sets, satisfy a common invariant, but make disjoint updates that collectively violate the invariant.
    - **The Doctor On-Call Dilemma**:
      - **Invariant**: At least one doctor must be on call at all times.
      - Currently, Doctor Alice and Doctor Bob are both on call.
      - Alice and Bob simultaneously request to take the night off:
        1. **Tx 1 (Alice)**: `SELECT COUNT(*) FROM doctors WHERE on_call = true` $\rightarrow$ Returns 2. Invariant satisfied!
        2. **Tx 2 (Bob)**: `SELECT COUNT(*) FROM doctors WHERE on_call = true` $\rightarrow$ Returns 2. Invariant satisfied!
        3. **Tx 1**: `UPDATE doctors SET on_call = false WHERE name = 'Alice'`.
        4. **Tx 2**: `UPDATE doctors SET on_call = false WHERE name = 'Bob'`.
        5. Both transactions commit successfully under `REPEATABLE READ`!
      - **Result**: Zero doctors are on call! The invariant is violated.
    - **Why Repeatable Read Fails**:
      - Repeatable Read guarantees that a transaction sees a snapshot of the database. It prevents phantom reads on the *read* side, but does not track cross-row relational constraints on the *write* side because Alice updated Alice's row while Bob updated Bob's row (no direct row collision).
    - **The Solution**:
      1. **Pessimistic Lock**: `SELECT * FROM doctors WHERE on_call = true FOR UPDATE`.
      2. **Serializable Isolation (SSI)**: In PostgreSQL, `SERIALIZABLE` detects read/write dependencies (SIREAD locks) and automatically aborts one transaction with `40001 serialization_failure`.
  </Accordion>

  <Accordion title="2. Compare Optimistic Locking vs Pessimistic Locking vs Atomic SQL Updates">
    | Locking Strategy | Mechanism | Best Use Case | Performance Under High Contention |
    | :--- | :--- | :--- | :--- |
    | **Optimistic Locking** (`@Version`) | Validates version number on commit: `UPDATE ... WHERE id = ? AND version = ?`. | Low-to-moderate contention (e.g., editing blog posts). | **Poor**. High abort/retry rates waste CPU and database cycles. |
    | **Pessimistic Locking** (`FOR UPDATE`) | Locks the database row immediately: `SELECT ... FOR UPDATE`. | Long-running transactions with multi-table invariants. | **Moderate**. Threads block and wait; potential deadlocks if ordering is inconsistent. |
    | **Atomic SQL Update** | In-place math guarded by predicate: `UPDATE inventory SET stock = stock - ? WHERE id = ? AND stock >= ?`. | High-contention flash sales & counter updates. | **Maximum**. Single round-trip, zero application retry loops, zero thread blocking. |
  </Accordion>

  <Accordion title="3. How does FOR UPDATE SKIP LOCKED enable high-throughput worker queues?">
    - **The Problem**:
      - 20 worker threads attempt to fetch the next pending task:
      ```sql
      SELECT * FROM tasks WHERE status = 'PENDING' ORDER BY id LIMIT 1 FOR UPDATE;
      ```
      - Thread 1 locks row 1.
      - Threads 2 through 20 all attempt to read row 1 and **block**, waiting for Thread 1 to commit.
      - Throughput collapses to 1 concurrent task at a time.
    - **The Solution (`SKIP LOCKED`)**:
      ```sql
      SELECT * FROM tasks WHERE status = 'PENDING' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED;
      ```
      - Thread 1 locks row 1.
      - Thread 2 attempts to read row 1, detects it is locked, **skips it immediately**, and locks row 2!
      - Thread 3 locks row 3.
      - All 20 threads process tasks in parallel with zero lock contention.
  </Accordion>

  <Accordion title="4. How does the Canonical Ordering Rule mathematically eliminate deadlocks?">
    - **The Deadlock Sequence**:
      - Tx 1 transfers money from Account A to Account B:
        1. Tx 1 locks Account A.
        2. Tx 2 transfers money from Account B to Account A: Tx 2 locks Account B.
        3. Tx 1 attempts to lock Account B $\rightarrow$ Blocks waiting for Tx 2.
        4. Tx 2 attempts to lock Account A $\rightarrow$ Blocks waiting for Tx 1.
        - **Deadlock detected**: The database terminates one transaction.
    - **The Canonical Ordering Rule**:
      - Whenever a transaction needs to acquire locks on multiple entities, it must **always acquire them in the exact same deterministic order** (e.g., sorted ascending by Primary Key).
      ```java
      Long firstLockId = Math.min(fromAccountId, toAccountId);
      Long secondLockId = Math.max(fromAccountId, toAccountId);

      accountRepository.lockById(firstLockId);
      accountRepository.lockById(secondLockId);
      ```
      - Because both transactions attempt to lock the lower ID first, Tx 2 blocks at Step 1 instead of acquiring lock B. A cyclic dependency is mathematically impossible.
  </Accordion>
</AccordionGroup>

## 5. API Architecture & Invariant Protection

<AccordionGroup>
  <Accordion title="1. Design an end-to-end distributed idempotency mechanism">
    - **The Failure Scenario**:
      - A customer clicks "Pay $100".
      - Backend charges Stripe and inserts an order into PostgreSQL.
      - Before the HTTP 200 response reaches the client, the mobile network drops.
      - The client automatically retries the `POST /v1/checkout` request. Without idempotency, the customer is charged $200.
    - **The Database-Backed Idempotency Pattern**:
      1. Client generates a unique UUID `Idempotency-Key` and sends it as an HTTP header.
      2. Backend creates an `idempotency_records` table:
         ```sql
         CREATE TABLE idempotency_records (
             key VARCHAR(64) PRIMARY KEY,
             status VARCHAR(32) NOT NULL, -- PENDING, COMPLETED, FAILED
             response_status INT,
             response_body JSONB,
             created_at TIMESTAMPTZ NOT NULL
         );
         ```
      3. In the database transaction:
         - Execute `INSERT INTO idempotency_records (key, status, ...) VALUES (?, 'PENDING', ...)`
         - If a unique constraint violation occurs (`409 Conflict` / `23505`):
           - If status is `COMPLETED`, return the cached `response_body` immediately without re-executing business logic.
           - If status is `PENDING`, return `409 Conflict` (request currently in-flight).
         - Execute payment and insert order.
         - Update idempotency record to `COMPLETED` with serialized response JSON.
  </Accordion>

  <Accordion title="2. Why are public setters an antipattern on domain entities?">
    - **Anemic Domain Anti-Pattern**:
      ```java
      Order order = new Order();
      order.setStatus("CONFIRMED"); // Bypassed inventory check!
      order.setTotalAmount(new BigDecimal("-50.00")); // Invariant broken: negative price!
      ```
      Public setters allow any developer, test, or controller to bypass business rules and place domain entities into mathematically impossible or corrupt states.
    - **Rich Domain Model (Invariant Defense)**:
      ```java
      public class Order {
          private OrderStatus status;
          private Money totalAmount;

          // No public setters!
          public void confirmPayment(PaymentReceipt receipt) {
              if (this.status != OrderStatus.PENDING) {
                  throw new IllegalStateException("Only pending orders can be confirmed");
              }
              if (!receipt.isSuccessful()) {
                  throw new PaymentFailedException("Receipt validation failed");
              }
              this.status = OrderStatus.CONFIRMED;
          }
      }
      ```
      All state transitions must occur through explicit domain methods that validate invariants before mutating private fields.
  </Accordion>
</AccordionGroup>

## 6. Real-World Production Debugging & Incident Response

<AccordionGroup>
  <Accordion title="1. How do you diagnose and resolve PostgreSQL Lock Queue Starvation?">
    - **The Incident**:
      - HikariCP pool exhausted. API returning 500 errors.
    - **The Diagnostic Query**:
      ```sql
      SELECT pid, usename, state, query_start, now() - query_start AS duration, query
      FROM pg_stat_activity
      WHERE state != 'idle'
      ORDER BY duration DESC;
      ```
    - **The Root Cause (The Lock Queue Trap)**:
      1. A slow reporting query runs `SELECT ... FROM orders` (taking 15 minutes, holding an `ACCESS SHARE` lock).
      2. A Flyway migration executes `ALTER TABLE orders ADD COLUMN flags INT;` (requests `ACCESS EXCLUSIVE` lock).
      3. PostgreSQL places `ALTER TABLE` in the lock queue waiting for the analytical read to finish.
      4. **The Trap**: PostgreSQL prioritizes pending exclusive locks over incoming shared locks. Every subsequent incoming fast `SELECT` from web traffic blocks behind the `ALTER TABLE` in the queue. Within 10 seconds, all 50 Tomcat threads block and HikariCP connection pool exhausts.
    - **The Emergency Mitigation**:
      ```sql
      -- Cancel the slow analytical read
      SELECT pg_cancel_backend(14201);

      -- If unresponsive, kill the process
      SELECT pg_terminate_backend(14201);
      ```
    - **The Prevention**:
      - Always set a lock timeout before migrations: `SET lock_timeout = '2s';`
  </Accordion>

  <Accordion title="2. Difference between JVM OOM and Kubernetes Exit Code 137 OOMKill">
    - **`java.lang.OutOfMemoryError: Java heap space`**:
      - The JVM process is alive. The garbage collector ran a Full GC, was unable to reclaim memory, and the allocated heap (`-Xmx`) was exceeded.
      - **Mitigation**: Trigger a heap dump automatically:
        `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps/oom.hprof` and analyze in Eclipse MAT.
    - **Kubernetes `Exit Code 137` (OOMKilled)**:
      - The Linux kernel OOM Killer sent `SIGKILL` (`128 + 9 = 137`) to the container.
      - The total memory consumed by the entire container (JVM Heap + Metaspace + Direct Memory + Thread Stacks + C runtime) exceeded the Kubernetes cgroup `resources.limits.memory`.
      - **Mitigation**:
        - Configure `-XX:MaxRAMPercentage=75.0` so the JVM leaves 25% of container RAM for off-heap buffers, OS overhead, and thread stacks.
  </Accordion>
</AccordionGroup>
