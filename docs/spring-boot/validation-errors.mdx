# Phase 1: Ground Floor (Physical First Principles)

## 1. Why Boundary Validation Protects Your Database

In backend engineering, **never trust client input**. An HTTP request body is just an unverified stream of raw bytes arriving over a TCP network socket.

```mermaid
flowchart LR
    Client["Untrusted Client<br/>(Browser / Mobile / Hacker)"] -->|"Raw JSON Bytes over TCP"| Controller["@RestController Boundary"]
    Controller -->|"1. Validate DTO"| Validator["Jakarta / Hibernate Validator"]
    Validator -->|Valid| Service["Domain Business Logic"]
    Validator -->|Invalid (400)| ErrorHandler["RFC 9457 ProblemDetail Handler"]
    Service -->|"2. Safe Clean Data"| DB[(PostgreSQL Database)]
```

If your application does not validate data at the HTTP entry boundary:
1. **Database Corruption**: Missing fields or negative prices slip into tables, corrupting financial ledgers and analytical reports.
2. **Security Vulnerabilities**: Malicious payloads, script injections (`XSS`), and buffer overflows can bypass weak checks.
3. **Wasted Compute**: Deep service calls, database connection checkouts, and external payment network calls execute only to crash on a missing `customerId` seconds later.

## 2. Jakarta Validation Under the Hood

Spring Boot uses **Hibernate Validator** (the reference implementation of Jakarta Bean Validation 3.0 / JSR-380).

### Starter Dependency

Validation is not included by default in `spring-boot-starter-web`. You must add `spring-boot-starter-validation`:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
```

When Spring Boot initializes, it configures a `LocalValidatorFactoryBean`. This bean:
1. Inspects your DTO classes using Java reflection and cached `MethodHandle` metadata.
2. Discovers constraint annotations (`@NotNull`, `@Size`, `@Email`).
3. Executes the corresponding `ConstraintValidator` logic whenever an incoming request is deserialized.

## Catastrophe 1: The Missing `@Valid` on Nested Objects

A developer built a checkout endpoint accepting an order with multiple items:

```java
// NAIVE CODE: NESTED ITEMS ARE SILENTLY NEVER VALIDATED!
public record CreateOrderRequest(
    @NotNull(message = "Customer ID is required")
    Long customerId,

    @NotEmpty(message = "Order must contain at least one item")
    List<OrderItemRequest> items // FATAL MISTAKE: Missing @Valid on the collection!
) {}

public record OrderItemRequest(
    @NotNull(message = "Product ID is required")
    Long productId,

    @Min(value = 1, message = "Quantity must be at least 1")
    int quantity,

    @Positive(message = "Price must be positive")
    BigDecimal price
) {}

@RestController
@RequestMapping("/api/orders")
public class OrderController {

    @PostMapping
    public ResponseEntity<Void> checkout(@Valid @RequestBody CreateOrderRequest request) {
        orderService.processOrder(request);
        return ResponseEntity.ok().build();
    }
}
```

### Why Production Crashes

The developer placed `@Valid` on `@RequestBody CreateOrderRequest`.

However, the client sends this JSON:
```json
{
  "customerId": 100,
  "items": [
    { "productId": null, "quantity": -5, "price": -50.00 }
  ]
}
```

**The Disaster**: Jakarta Validation evaluates `customerId` (valid) and `items` (not empty). **It does NOT inspect the fields inside `OrderItemRequest`!**

Without `@Valid` directly on the collection property, validation does **not cascade**. Negative quantities and null product IDs pass directly to the database, corrupting stock counts and selling items for negative money!

### The Fix: Explicit Cascading Validation

```java
public record CreateOrderRequest(
    @NotNull(message = "Customer ID is required")
    Long customerId,

    @NotEmpty(message = "Order must contain at least one item")
    List<@Valid OrderItemRequest> items // CASCADES validation into every item!
) {}
```

Line by line:
- `List<@Valid OrderItemRequest> items`: Instructs Hibernate Validator to cascade validation down into each individual element in the list. Any invalid item immediately halts execution with a 400 Bad Request.

## Catastrophe 2: `@Valid` vs `@Validated` on Query & Path Parameters

A developer added path and query parameter constraints to a user search endpoint:

```java
// NAIVE CODE: PATH AND QUERY CONSTRAINTS ARE SILENTLY IGNORED!
@RestController
@RequestMapping("/api/users")
public class UserController {

    @GetMapping("/{id}")
    public UserResponse getUser(
        @PathVariable @Min(1) Long id // FATAL MISTAKE: @Min is completely ignored!
    ) {
        return userService.findById(id);
    }

    @GetMapping
    public List<UserResponse> searchUsers(
        @RequestParam @Size(min = 3, max = 50) String query // FATAL MISTAKE: Ignored!
    ) {
        return userService.search(query);
    }
}
```

### Why Production Fails

A user requests `GET /api/users/-99` or `GET /api/users?query=a`.

The developer expected `@Min(1)` and `@Size(min = 3)` to reject the requests with `400 Bad Request`. Instead, **the methods execute normally**!

#### Why It Failed
- `@Valid` and method argument validation only work automatically on **`@RequestBody` DTOs** dispatched by `HandlerMethodArgumentResolver`.
- Query parameters (`@RequestParam`) and Path variables (`@PathVariable`) are simple Java types (`Long`, `String`). Spring MVC does **not** validate them unless the controller class itself is advised by Spring's `MethodValidationPostProcessor`.

### The Fix: Add `@Validated` at Class Level

```java
@RestController
@RequestMapping("/api/users")
@Validated // MANDATORY: Activates AOP method validation proxy on controller methods!
public class UserController {

    @GetMapping("/{id}")
    public UserResponse getUser(@PathVariable @Min(1) Long id) {
        return userService.findById(id);
    }

    @GetMapping
    public List<UserResponse> searchUsers(
        @RequestParam @NotBlank @Size(min = 3, max = 50) String query
    ) {
        return userService.search(query);
    }
}
```

<Warning>
**The Critical Exception Type Difference**:
- Validating `@RequestBody` with `@Valid` throws **`MethodArgumentNotValidException`**.
- Validating `@PathVariable` or `@RequestParam` with class-level `@Validated` throws **`ConstraintViolationException`**!
Your global exception handler must handle **both** exception types, otherwise parameter violations will return `500 Internal Server Error` instead of `400 Bad Request`!
</Warning>

# Phase 3: Under the Hood (Mechanics & Custom Validators)

## 1. Creating Production-Grade Custom Constraint Validators

Standard annotations (`@NotNull`, `@Size`) cannot validate domain-specific formats like strong passwords, phone numbers, or tax IDs.

Here is how to build a production-grade `@StrongPassword` validator:

### Step 1: Define the Annotation

```java
package com.example.validation;

import jakarta.validation.Constraint;
import jakarta.validation.Payload;
import java.lang.annotation.*;

@Documented
@Constraint(validatedBy = StrongPasswordValidator.class) // Links to the physical validator
@Target({ ElementType.FIELD, ElementType.PARAMETER, ElementType.RECORD_COMPONENT })
@Retention(RetentionPolicy.RUNTIME)
public @interface StrongPassword {

    String message() default "Password must be at least 8 characters long, contain at least 1 digit, 1 uppercase letter, and 1 special symbol";

    Class<?>[] groups() default {};

    Class<? extends Payload>[] payload() default {};
}
```

### Step 2: Implement `ConstraintValidator`

```java
package com.example.validation;

import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;
import java.util.regex.Pattern;

public class StrongPasswordValidator implements ConstraintValidator<StrongPassword, String> {

    // Regex: >= 8 chars, >= 1 uppercase, >= 1 digit, >= 1 special character
    private static final Pattern PASSWORD_PATTERN = Pattern.compile(
        "^(?=.*[0-9])(?=.*[A-Z])(?=.*[@#$%^&+=!])(?=\\S+$).{8,}$"
    );

    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        // In Jakarta Bean Validation, null checks should be handled by @NotNull
        if (value == null) {
            return true;
        }

        return PASSWORD_PATTERN.matcher(value).matches();
    }
}
```

### Step 3: Use in DTO

```java
public record RegisterUserRequest(
    @NotBlank String email,
    @NotNull @StrongPassword String password
) {}
```

## 2. Cross-Field Validation (Class-Level Constraints)

Sometimes a rule involves two fields (e.g. `startDate` must be before `endDate`, or `password` must match `confirmPassword`):

```java
package com.example.validation;

import jakarta.validation.Constraint;
import jakarta.validation.Payload;
import java.lang.annotation.*;

@Documented
@Constraint(validatedBy = DateRangeValidator.class)
@Target({ ElementType.TYPE }) // Class-level constraint!
@Retention(RetentionPolicy.RUNTIME)
public @interface ValidDateRange {
    String message() default "Start date must be strictly before end date";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}
```

```java
package com.example.validation;

import com.example.dto.BookingRequest;
import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;

public class DateRangeValidator implements ConstraintValidator<ValidDateRange, BookingRequest> {

    @Override
    public boolean isValid(BookingRequest booking, ConstraintValidatorContext context) {
        if (booking == null || booking.startDate() == null || booking.endDate() == null) {
            return true;
        }

        boolean isValid = booking.startDate().isBefore(booking.endDate());

        if (!isValid) {
            // Attach the error specifically to the "endDate" property for clean UI mapping
            context.disableDefaultConstraintViolation();
            context.buildConstraintViolationWithTemplate(context.getDefaultConstraintMessageTemplate())
                .addPropertyNode("endDate")
                .addConstraintViolation();
        }

        return isValid;
    }
}
```

## 3. Validation Groups (Conditional Validation without Duplicate DTOs)

In REST APIs, creating a resource often requires fields that are forbidden or optional during an update (e.g., `id` is null on `POST`, but mandatory on `PUT`):

Instead of maintaining duplicate `CreateUserRequest` and `UpdateUserRequest` classes, use **Validation Groups**:

### Step 1: Define Marker Interfaces

```java
package com.example.validation;

public interface ValidationGroups {
    interface OnCreate {}
    interface OnUpdate {}
}
```

### Step 2: Annotate DTO Fields with Groups

```java
public record UserDto(
    @Null(groups = ValidationGroups.OnCreate.class, message = "ID must be null when creating a user")
    @NotNull(groups = ValidationGroups.OnUpdate.class, message = "ID is required when updating a user")
    Long id,

    @NotBlank(groups = {ValidationGroups.OnCreate.class, ValidationGroups.OnUpdate.class})
    String name,

    @NotBlank(groups = ValidationGroups.OnCreate.class)
    @Null(groups = ValidationGroups.OnUpdate.class, message = "Email cannot be updated")
    String email
) {}
```

### Step 3: Activate in Controller using `@Validated`

```java
@RestController
@RequestMapping("/api/users")
public class UserController {

    @PostMapping
    public ResponseEntity<Void> createUser(
        @Validated(ValidationGroups.OnCreate.class) @RequestBody UserDto dto
    ) {
        userService.create(dto);
        return ResponseEntity.status(HttpStatus.CREATED).build();
    }

    @PutMapping("/{id}")
    public ResponseEntity<Void> updateUser(
        @PathVariable Long id,
        @Validated(ValidationGroups.OnUpdate.class) @RequestBody UserDto dto
    ) {
        userService.update(id, dto);
        return ResponseEntity.ok().build();
    }
}
```

## 4. RFC 9457 / RFC 7807 `ProblemDetail` Architecture

Spring Boot 3 natively adopts **RFC 9457** (the successor to RFC 7807) for standardized HTTP API problem details.

### Enabling Problem Details Globally

In `application.yml`:
```yaml
spring:
  mvc:
    problemdetails:
      enabled: true
```

### Production Global Exception Handler (`ResponseEntityExceptionHandler`)

Instead of writing custom ad-hoc error response classes, extend Spring's `ResponseEntityExceptionHandler` to standardize all errors into RFC 9457 `ProblemDetail`:

```java
package com.example.exception;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.validation.ConstraintViolation;
import jakarta.validation.ConstraintViolationException;
import org.slf4j.MDC;
import org.springframework.http.*;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.context.request.ServletWebRequest;
import org.springframework.web.context.request.WebRequest;
import org.springframework.web.servlet.mvc.method.annotation.ResponseEntityExceptionHandler;

import java.net.URI;
import java.time.Instant;
import java.util.LinkedHashMap;
import java.util.Map;

@RestControllerAdvice
public class GlobalApiExceptionHandler extends ResponseEntityExceptionHandler {

    // 1. Handle DTO validation failures (@Valid @RequestBody)
    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
        MethodArgumentNotValidException ex,
        HttpHeaders headers,
        HttpStatusCode status,
        WebRequest request
    ) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
            HttpStatus.BAD_REQUEST,
            "One or more fields in the request failed validation."
        );
        problem.setTitle("Validation Failed");
        problem.setType(URI.create("https://api.example.com/errors/validation-failed"));

        // Extract clean field-level errors
        Map<String, String> fieldErrors = new LinkedHashMap<>();
        for (FieldError fieldError : ex.getBindingResult().getFieldErrors()) {
            fieldErrors.put(fieldError.getField(), fieldError.getDefaultMessage());
        }

        problem.setProperty("invalidFields", fieldErrors);
        problem.setProperty("timestamp", Instant.now());
        problem.setProperty("traceId", MDC.get("traceId"));

        return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(problem);
    }

    // 2. Handle Path/Query parameter validation failures (@Validated on Controller)
    @ExceptionHandler(ConstraintViolationException.class)
    public ResponseEntity<ProblemDetail> handleConstraintViolation(
        ConstraintViolationException ex,
        HttpServletRequest request
    ) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
            HttpStatus.BAD_REQUEST,
            "One or more query parameters or path variables are invalid."
        );
        problem.setTitle("Parameter Constraint Violation");
        problem.setType(URI.create("https://api.example.com/errors/constraint-violation"));

        Map<String, String> errors = new LinkedHashMap<>();
        for (ConstraintViolation<?> violation : ex.getConstraintViolations()) {
            errors.put(violation.getPropertyPath().toString(), violation.getMessage());
        }

        problem.setProperty("invalidParameters", errors);
        problem.setProperty("timestamp", Instant.now());
        problem.setProperty("traceId", MDC.get("traceId"));

        return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(problem);
    }

    // 3. Handle Resource Not Found
    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ProblemDetail> handleNotFound(ResourceNotFoundException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        problem.setTitle("Resource Not Found");
        problem.setType(URI.create("https://api.example.com/errors/not-found"));
        problem.setProperty("timestamp", Instant.now());
        problem.setProperty("traceId", MDC.get("traceId"));
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(problem);
    }

    // 4. Catch-all for unexpected internal server errors (Fail-safe)
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ProblemDetail> handleGenericException(Exception ex) {
        // In production: Log the full stack trace with trace ID
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
            HttpStatus.INTERNAL_SERVER_ERROR,
            "An unexpected internal server error occurred. Please contact support with the trace ID."
        );
        problem.setTitle("Internal Server Error");
        problem.setType(URI.create("https://api.example.com/errors/internal-error"));
        problem.setProperty("timestamp", Instant.now());
        problem.setProperty("traceId", MDC.get("traceId"));
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(problem);
    }
}
```

## Active Recall & Interview Mastery

<AccordionGroup>
  <Accordion title="1. What is the fundamental difference between MethodArgumentNotValidException and ConstraintViolationException?">
    `MethodArgumentNotValidException` is thrown by Spring MVC when `@Valid @RequestBody` fails validation during Jackson deserialization in `RequestResponseBodyMethodProcessor`. `ConstraintViolationException` is thrown by Hibernate Validator via Spring's AOP `MethodValidationPostProcessor` when `@Validated` is placed on a controller class to validate individual `@PathVariable` or `@RequestParam` parameters. They require separate handler methods in `@RestControllerAdvice`.
  </Accordion>

  <Accordion title="2. How do you implement cascading validation on nested objects and collections?">
    To cascade validation down into child objects or collections, you must annotate the member field or collection type parameter with `@Valid`. For example: `List<@Valid ItemDto> items` or `@Valid AddressDto shippingAddress`. Without `@Valid`, the validator only inspects top-level annotations (like `@NotNull` or `@NotEmpty`) and skips the internal fields of the child objects entirely.
  </Accordion>

  <Accordion title="3. What is RFC 9457 ProblemDetail, and why should modern Spring Boot 3 APIs use it?">
    RFC 9457 (which obsoletes RFC 7807) defines a standardized, machine-readable HTTP response format for reporting errors. It standardizes five core fields: `type` (URI reference), `title` (summary), `status` (HTTP code), `detail` (explanation), and `instance` (request URI). Adopting ProblemDetail avoids creating fragmented custom error formats, enabling API gateways, web clients, and third-party SDKs to parse and handle errors consistently across microservices.
  </Accordion>

  <Accordion title="4. How do Validation Groups work, and when should you use them?">
    Validation Groups allow applying different validation rules to the same DTO based on context (e.g. `OnCreate` vs `OnUpdate`). You define marker interfaces and assign them to constraints: `@Null(groups = OnCreate.class)` and `@NotNull(groups = OnUpdate.class)`. In the controller, you annotate the DTO with `@Validated(OnCreate.class)`. This eliminates the need to maintain redundant, duplicate request DTO classes for create and update operations.
  </Accordion>

  <Accordion title="5. How do you implement cross-field validation in Spring Boot?">
    Cross-field validation (e.g., verifying `startDate` is before `endDate`) is implemented by creating a custom constraint annotation with `@Target(ElementType.TYPE)` placed at the class level of the DTO. The corresponding `ConstraintValidator` receives the entire DTO instance in `isValid(dto, context)`, allowing it to compare multiple fields and attach custom property violations to specific nodes using `context.buildConstraintViolationWithTemplate()`.
  </Accordion>

  <Accordion title="6. Why should you extend ResponseEntityExceptionHandler instead of writing ad-hoc @ExceptionHandler methods?">
    `ResponseEntityExceptionHandler` is Spring MVC's official base class containing pre-built handling for all 15 standard Spring MVC exceptions (e.g. `HttpRequestMethodNotSupportedException`, `HttpMediaTypeNotSupportedException`, `MissingServletRequestParameterException`, `MethodArgumentNotValidException`). Extending it ensures that all framework-level routing and binding errors are consistently caught and transformed into standard `ProblemDetail` responses rather than slipping through as unformatted 500 errors.
  </Accordion>

  <Accordion title="7. Why should validation messages avoid leaking internal database column names or raw exception details?">
    Leaking database column names, raw SQL fragments, or unhandled stack traces exposes internal system implementation details to attackers, aiding SQL injection and schema reconnaissance. Furthermore, clients expect API errors mapped to the JSON contract field names they sent (`firstName`), not internal database column names (`usr_fst_nm_txt`).
  </Accordion>

  <Accordion title="8. How do you inject a distributed trace ID into RFC 9457 ProblemDetail responses?">
    By using SLF4J's Mapped Diagnostic Context (`MDC`) populated by an incoming HTTP filter or Spring Cloud Sleuth / Micrometer Tracing. Inside `@RestControllerAdvice`, retrieve the trace ID via `MDC.get("traceId")` and attach it to the `ProblemDetail` object via `problem.setProperty("traceId", traceId)`. This allows frontend users and customer support to correlate UI errors directly with backend logs in Datadog or Grafana Tempo.
  </Accordion>
</AccordionGroup>
