## 1. Mental Model: Why Relational Databases Fail at Search

Relational databases like PostgreSQL are optimized for point lookups and range scans on structured data using B-Trees. However, when users type unstructured queries into a search bar:
- `SELECT * FROM products WHERE description LIKE '%wireless headphones%'`
- `SELECT * FROM articles WHERE content ILIKE '%kubernetes cluster%'`

A standard B-Tree index is **completely useless**. Because the search term contains a leading wildcard (`%`), the PostgreSQL query planner must perform a **Sequential Scan** (`Seq Scan`) across every single 8KB disk page in the multi-gigabyte table:

```mermaid
flowchart TD
    subgraph Relational Table Scan: O(N) Disk IO
        Q["User Query: 'wireless headphones'"] --> Scan[PostgreSQL Seq Scan]
        Scan --> P1["Row 1: Read full text from disk"]
        Scan --> P2["Row 2: Read full text from disk"]
        Scan --> PN["Row 10,000,000: Full Disk Read"]
        PN --> Match["Filter matches with zero relevance ranking<br/>Latency: 4,200ms"]
    end
```

Furthermore, relational databases lack:
1. **Relevance Ranking**: Calculating how central a keyword is to a document (TF-IDF / BM25).
2. **Linguistic Processing**: Stemming (`running` $\rightarrow$ `run`), lemmatization, synonym expansion, and typo tolerance (fuzzy Levenshtein distance).
3. **Semantic Understanding**: Knowing that `laptop sleeve` is conceptually related to `computer case`.

To solve this, modern backends pair relational systems of record with **Inverted Index Search Engines** (Elasticsearch / OpenSearch) and **Vector Databases** (`pgvector`).

## 2. Apache Lucene Storage Internals

Elasticsearch and OpenSearch are distributed wrappers around **Apache Lucene**. Lucene turns the relational data model upside down: instead of mapping documents to text fields, an **Inverted Index** maps vocabulary words to the list of documents containing them:

```mermaid
flowchart LR
    subgraph Raw Documents
        D1["Doc 1: Spring Boot Microservices"]
        D2["Doc 2: Microservices with Docker"]
        D3["Doc 3: Docker and Kubernetes"]
    end

    subgraph Lucene Inverted Index
        T1["boot"] --> L1["[Doc 1]"]
        T2["docker"] --> L2["[Doc 2, Doc 3]"]
        T3["kubernetes"] --> L3["[Doc 3]"]
        T4["microservices"] --> L4["[Doc 1, Doc 2]"]
        T5["spring"] --> L5["[Doc 1]"]
    end
```

### The Three Core Structures of an Inverted Index

```console
+-------------------------------------------------------------+
| 1. Term Dictionary (FST - Finite State Transducer in RAM)   |
|    "docker" -> Pointer to Term Index                        |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
| 2. Postings List (Roaring Bitmaps on Disk)                  |
|    Doc IDs: [2, 3]                                          |
|    Term Frequencies: [Doc 2: 1, Doc 3: 1]                   |
|    Positions: [Doc 2: pos 3, Doc 3: pos 1]                  |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
| 3. Stored Fields & Doc Values (Columnar Storage)            |
|    Fast sorting, aggregations, and original source payload  |
+-------------------------------------------------------------+
```

1. **Term Dictionary & Finite State Transducer (FST)**:
   - Stores all unique terms sorted alphabetically.
   - Compressed into memory using a Finite State Transducer (FST), enabling $O(\text{term length})$ prefix and wildcard lookups without loading terms from disk.
2. **Postings List with Roaring Bitmaps**:
   - An array of Document IDs containing the term, along with term frequency and byte offsets for phrase matching.
   - Compressed using **Roaring Bitmaps** for ultra-fast bitwise intersections (`AND` queries) and unions (`OR` queries).
3. **Doc Values (Columnar Format)**:
   - While inverted indexes map `term -> docs` (ideal for search), aggregations and sorting require `doc -> terms`. Doc Values provide a columnar on-disk layout enabling instant sorting by price, date, or category.

### BM25: The Relevance Scoring Math
Lucene ranks search results using **BM25 (Best Matching 25)**:

$$\text{Score}(D, Q) = \sum_{i=1}^{N} \text{IDF}(q_i) \cdot \frac{f(q_i, D) \cdot (k_1 + 1)}{f(q_i, D) + k_1 \cdot \left(1 - b + b \cdot \frac{|D|}{\text{avgdl}}\right)}$$

- **$\text{IDF}(q_i)$ (Inverse Document Frequency)**: Rare words (e.g., `kubernetes`) carry high weight; common stop words (e.g., `the`, `and`) carry near-zero weight.
- **$f(q_i, D)$ (Term Frequency)**: How many times term $q_i$ appears in document $D$, throttled by saturation parameter $k_1$ so repeating a word 100 times doesn't break relevance.
- **$\frac{|D|}{\text{avgdl}}$ (Document Length Normalization)**: Penalizes long, spammy documents so concise, highly relevant documents rank higher.

## 3. The Dual-Write Anti-Pattern & Disaster

How do you keep PostgreSQL (your transactional source of truth) synchronized with Elasticsearch?

### The Naive Approach (Application Dual-Writes):
```java
// DANGEROUS ANTI-PATTERN: DO NOT USE IN PRODUCTION
@Transactional
public Order createOrder(OrderRequest request) {
    Order order = orderRepository.save(new Order(request)); // Write 1: PostgreSQL
    searchClient.index(new OrderSearchDoc(order));          // Write 2: Elasticsearch
    return order;
}
```

```mermaid
sequenceDiagram
    autonumber
    participant App as Spring Boot Service
    participant DB as PostgreSQL (System of Record)
    participant ES as OpenSearch / Elasticsearch

    App->>DB: 1. INSERT INTO orders (...)
    Note over DB: Transaction commits successfully
    App->>ES: 2. PUT /orders/_doc/101
    Note over ES: Network timeout or Elasticsearch node crash!
    ES-->>App: 3. HTTP 504 Gateway Timeout
    Note over App: DB committed, but ES missed the write!<br/>Permanent silent data drift.
```

### Why Dual-Writes Inevitably Corrupt Data:
1. **Partial Failures**: If Step 1 succeeds and Step 2 fails, your database has an order that never appears in search.
2. **Rollback Desynchronization**: If Step 1 succeeds, Step 2 succeeds, but a downstream database constraint triggers a transaction rollback, Elasticsearch contains a **phantom document** that physically does not exist in the database!
3. **Out-of-Order Race Conditions**: Two concurrent threads update the same record. Thread A writes to DB at $T_1$ and Thread B writes to DB at $T_2$. Due to network jitter, Thread A's search update arrives at Elasticsearch **after** Thread B's update, permanently overwriting the newer state with stale data.

## 4. Rock-Solid CDC Pipeline: PostgreSQL WAL to OpenSearch

To eliminate dual-writes, production systems decouple writes using **Change Data Capture (CDC)** reading directly from the PostgreSQL Write-Ahead Log (WAL):

```mermaid
flowchart LR
    subgraph Transactional Core
        Client[Client Request] --> App[Spring Boot App]
        App -->|Single Atomic Transaction| PG[(PostgreSQL)]
        PG -->|Logical Decoding pgoutput| WAL[Write-Ahead Log]
    end

    subgraph Streaming Ingestion
        WAL -->|Streams low-level change events| Debezium[Debezium CDC Connector]
        Debezium -->|Guaranteed At-Least-Once| Kafka[Apache Kafka: orders.cdc]
    end

    subgraph Search Indexing
        Kafka -->|Consumes stream| Consumer[OpenSearch Ingestion Worker]
        Consumer -->|Batch Bulk Indexing| ES[(OpenSearch Cluster)]
    end
```

### 1. PostgreSQL Logical Replication Configuration (`postgresql.conf`)
```ini
wal_level = logical
max_wal_senders = 4
max_replication_slots = 4
```

Line by line:

- `wal_level = logical` makes PostgreSQL include enough information in WAL for logical decoding. Without it, Debezium cannot reconstruct row-level change events.
- `max_wal_senders = 4` allows replication sender processes to stream WAL to standbys or logical consumers.
- `max_replication_slots = 4` allows PostgreSQL to track retention positions for replicas/connectors.

Operational risk: every replication slot is a retention promise. If a Debezium connector stops, the primary keeps WAL until the connector catches up or the slot is advanced/dropped. Monitor slot lag like production disk risk, not like a harmless metric.

### 2. Idempotent Indexing with Versioning
To prevent out-of-order Kafka message deliveries from overwriting newer records, configure Elasticsearch external versioning:

```http
PUT /products/_doc/1001?version=1740837190000&version_type=external_gte
{
  "title": "Noise Cancelling Headphones",
  "price": 299.99,
  "updated_at": 1740837190000
}
```

Line by line:

- `PUT /products/_doc/1001` writes document ID `1001`, matching the source database primary key.
- `version=1740837190000` supplies the source ordering value, usually an update timestamp, LSN-derived value, or monotonically increasing version.
- `version_type=external_gte` tells Elasticsearch/OpenSearch to accept this write only if its version is greater than or equal to the stored document version.
- `title`, `price`, and `updated_at` are the denormalized search document fields, not the transactional source of truth.

What breaks without versioning:

```console
Event A: product price = 299, version 10
Event B: product price = 249, version 11
Network delay delivers B first, then A second
Without versioning, stale event A overwrites the newer price
With external versioning, event A is rejected
```

Proof task:

```console
Index document version 11.
Try indexing older version 10.
Verify the search engine rejects or ignores the stale update.
Then replay the same version 11 event and confirm idempotent behavior.
```
If an out-of-order event arrives with a `version` (timestamp) lower than the version currently stored in Elasticsearch, Elasticsearch rejects the write with `409 Conflict`, guaranteeing eventual consistency.

### 3. The Transactional Outbox Pattern with Debezium SMT

Capturing changes directly from primary entity tables (e.g. streaming raw rows from the `orders` table) creates severe architectural coupling:
- **Internal Schema Leakage**: Any internal table restructuring immediately breaks external downstream consumers.
- **Intermediate State Pollution**: Rapid multi-step transactions emit noisy intermediate states instead of clean domain events.

#### The Transactional Outbox Solution:
The application writes its business state to the primary table and simultaneously writes a curated domain event into an **Outbox Table** in the exact same atomic local ACID transaction:

```sql
CREATE TABLE outbox_events (
    id UUID PRIMARY KEY,
    aggregate_type VARCHAR(64) NOT NULL,   -- e.g. "Order", "Product"
    aggregate_id VARCHAR(64) NOT NULL,     -- e.g. "order_1001" (Kafka Partition Key)
    event_type VARCHAR(64) NOT NULL,       -- e.g. "OrderCreated", "ProductUpdated"
    payload JSONB NOT NULL,                -- Curated domain payload for Elasticsearch
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);
```

```java
// Spring Boot Service: Atomic write of business entity and outbox event
@Transactional
public Order createOrder(OrderRequest request) {
    Order order = orderRepository.save(new Order(request));

    OutboxEvent event = new OutboxEvent(
        UUID.randomUUID(),
        "Order",
        String.valueOf(order.getId()),
        "OrderCreated",
        objectMapper.writeValueAsString(new OrderSearchDTO(order))
    );
    outboxRepository.save(event);

    return order; // Commits atomically! Zero dual-write risk!
}
```

#### Debezium Outbox Event Router SMT:
Configure Debezium in Kafka Connect with the **Outbox Event Router** Single Message Transformation (SMT). It reads the `outbox_events` table from the WAL, routes each event to a topic named after `aggregate_type` (`orders.events`), partitions by `aggregate_id`, unwraps the `payload` JSON, and automatically discards internal CDC metadata:

```json
{
  "name": "debezium-outbox-connector",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "tasks.max": "1",
    "plugin.name": "pgoutput",
    "database.hostname": "postgres.internal",
    "database.port": "5432",
    "database.user": "debezium_cdc",
    "database.password": "${file:/secrets/db:cdc_password}",
    "database.dbname": "production_db",
    "database.server.name": "pg_core",
    "table.include.list": "public.outbox_events",
    "tombstones.on.delete": "false",
    "transforms": "outbox",
    "transforms.outbox.type": "io.debezium.transforms.outbox.EventRouter",
    "transforms.outbox.route.by.field": "aggregate_type",
    "transforms.outbox.route.topic.replacement": "${routedByValue}.events"
  }
}
```

### 4. The Catastrophic Unconsumed Replication Slot Disk Outage

The single most dangerous operational hazard of PostgreSQL Change Data Capture is **Replication Slot Abandonment**.

```mermaid
sequenceDiagram
    autonumber
    participant PG as PostgreSQL Primary (NVMe SSD)
    participant Slot as Logical Replication Slot (pgoutput)
    participant Deb as Debezium Worker (Kafka Connect)
    
    Note over PG,Slot: Debezium runs normally. Slot restart_lsn advances with WAL flushes.
    Note over Deb: KAFKA CONNECT POD CRASHES OR NETWORK PARTITION OCCURS!
    Note over Deb: Debezium goes offline for 18 hours over the weekend!
    
    loop Incoming Customer Transactions
        PG->>PG: Continuous INSERT, UPDATE, DELETE generate 200 GB of WAL!
    end
    
    Note over PG: PostgreSQL checkpointer attempts to delete recycled WAL segments...
    Slot-->>PG: STOP! Slot holds restart_lsn from 18 hours ago!
    Note over PG: PostgreSQL CANNOT delete any WAL segments newer than restart_lsn!
    Note over PG: WAL directory (/var/lib/postgresql/data/pg_wal) swells from 2GB to 500GB!
    Note over PG: Physical NVMe SSD reaches 100% capacity!
    Note over PG: POSTGRESQL PANICS AND SHUTS DOWN! Total database blackout!
```

#### Why Production Crashed:
When a logical replication slot is registered, PostgreSQL makes an absolute durability promise: *"I will never delete any Write-Ahead Log segment that this slot has not yet confirmed receiving."* 

If Debezium crashes or Kafka rejects writes, the slot's `restart_lsn` stops moving. As application transactions proceed, PostgreSQL retains **every single 16MB WAL file on disk indefinitely**. Within hours or days, the server's physical storage hits $100\%$, and PostgreSQL terminates immediately (`PANIC: could not write to file ... No space left on device`).

#### Staff Defense 1: Set `max_slot_wal_keep_size`
PostgreSQL provides a circuit breaker to sacrifice the CDC replication slot to save the database server from a fatal disk outage:

```ini
# postgresql.conf

# Cap the maximum WAL retained for all replication slots to 64 GB
max_slot_wal_keep_size = 64GB
```

If Debezium remains offline long enough for accumulated WAL to reach 64 GB, PostgreSQL **invalidates the replication slot** (`wal_status = 'lost'`) and deletes the old WAL segments, keeping the database online. Debezium will fail when restarted and require a fresh snapshot, but live customer checkout traffic never drops!

#### Staff Defense 2: Automated Replication Slot Monitoring:
```sql
SELECT 
    slot_name,
    plugin,
    active,
    wal_status,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal_size,
    round(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) / (1024.0 * 1024.0 * 1024.0), 2) AS retained_wal_gb
FROM pg_replication_slots;
```

Configure Prometheus alerts to page on-call engineers if any slot's `retained_wal_gb` exceeds **10 GB**.

## 5. Mitigating "Search After Write" Eventual Consistency

Because CDC pipelines are asynchronous, there is a replication lag (typically 50ms - 500ms) between committing to PostgreSQL and appearing in Elasticsearch. Additionally, Elasticsearch has a default **Refresh Interval** of 1 second (`index.refresh_interval: 1s`) before newly indexed documents become visible to queries.

```mermaid
sequenceDiagram
    autonumber
    participant User as Browser / Mobile App
    participant API as Spring Boot API
    participant PG as PostgreSQL
    participant ES as OpenSearch

    User->>API: 1. POST /products (Create product)
    API->>PG: 2. INSERT INTO products
    API-->>User: 3. HTTP 201 Created (Product ID: 42)
    User->>API: 4. GET /products?q=my-new-product (Immediate search redirect)
    API->>ES: 5. Search query
    Note over ES: CDC replication lag or unrefreshed index!<br/>Product 42 not visible yet.
    ES-->>API: 6. Returns [] (Empty list!)
    API-->>User: 7. "No products found" (User confusion!)
```

### Production Mitigations for Search-After-Write:
1. **Optimistic Local UI State**: The client SPA immediately appends the newly created item to its local UI list, bypassing an immediate full-text search query.
2. **Read-Your-Own-Writes Fallback**: If a search query is accompanied by a recently created ID header, query PostgreSQL by primary key directly if the search index returns empty.
3. **Targeted Refresh**: In low-throughput administrative back-offices (CMS tools), pass `?refresh=wait_for` on individual writes to block the client response until the Lucene segment refreshes.

## 6. Modern AI Semantic Search with `pgvector`

What if you want semantic vector similarity search without managing a dedicated multi-node Elasticsearch cluster?

PostgreSQL provides **`pgvector`**, allowing high-dimensional vector embeddings to live directly alongside relational tables.

```mermaid
flowchart TD
    subgraph Semantic Vector Pipeline
        Text["Product: 'Noise cancelling over-ear headphones'"] --> AI[Embedding Model: OpenAI / Ollama / Spring AI]
        AI -->|Produces 1536-dim Float Array| Vec["[0.0124, -0.0482, 0.8912, ...]"]
        Vec --> SQL["INSERT INTO products (title, embedding) VALUES (...)"]
        SQL --> PG[(PostgreSQL + pgvector)]
    end
```

### PostgreSQL Vector DDL & Distance Metrics

```sql
-- 1. Enable pgvector extension
CREATE EXTENSION IF NOT EXISTS vector;

-- 2. Create products table with 1536-dimensional vector column
CREATE TABLE product_embeddings (
    id BIGINT PRIMARY KEY,
    title VARCHAR(255) NOT NULL,
    description TEXT,
    embedding vector(1536) NOT NULL
);

-- 3. Create Hierarchical Navigable Small World (HNSW) Index
CREATE INDEX idx_products_embedding_hnsw 
ON product_embeddings 
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);
```

### HNSW vs IVFFlat Indexing Comparison

| Vector Index Type | Build Speed | Query Latency | Recall Accuracy | Memory Footprint |
| :--- | :--- | :--- | :--- | :--- |
| **IVFFlat (Inverted File Flat)** | Fast | Moderate | ~85-90% | Low |
| **HNSW (Hierarchical Navigable Small World)** | Slow | **Ultra-Fast (sub-5ms)** | **~98-99%** | High (Entire graph in RAM) |

### Vector Similarity Distance Operators:
- `<=>` : **Cosine Distance** (most common for text embeddings; measures angle between vectors, independent of magnitude).
- `<->` : **Euclidean Distance ($L_2$)** (measures physical distance between points).
- `<#>` : **Negative Inner Product** (used for normalized embeddings).

```sql
-- Semantic Search Query: Find top 5 items most similar to user search embedding
SELECT id, title, 1 - (embedding <=> :queryEmbedding) AS similarity_score
FROM product_embeddings
ORDER BY embedding <=> :queryEmbedding
LIMIT 5;
```

### HNSW Graph Physics & Memory Sizing Mathematics

Hierarchical Navigable Small World (HNSW) graphs are the state-of-the-art data structure for vector similarity search:

```mermaid
flowchart TD
    subgraph HNSWLayers ["Multi-Layer HNSW Graph (Probabilistic Skip-List)"]
        L2["Layer 2 (Sparse): Long-range hops across vector space"]
        L1["Layer 1 (Medium): Medium-range navigation"]
        L0["Layer 0 (Dense): Contains ALL 1,000,000 vectors with local neighbor links"]
    end
    
    Query["Search Vector"] --> L2
    L2 -->|Greedy routing to closest local node| L1
    L1 -->|Greedy routing to closest local node| L0
    L0 -->|Refines nearest neighbors| Result["Top K Matches (Cosine Distance)"]
```

#### Tuning the Parameter Trinity:
1. **`m` (Max Outgoing Links per Node, default: 16)**:
   - Dictates how many bidirectional connections each vector maintains to its neighbors.
   - Increasing `m` (e.g., to `32` or `64`) improves recall accuracy and provides faster searches, but proportionally increases RAM consumption and index build time.
2. **`ef_construction` (Build-Time Candidate Queue, default: 64)**:
   - Dictates the depth of exploration during `CREATE INDEX`. Higher values (e.g., `128` or `256`) produce a higher quality graph topology with fewer disjoint clusters, without increasing index RAM size after the build completes!
3. **`hnsw.ef_search` (Query-Time Beam Size, default: 40)**:
   - Dynamic session-level parameter governing search accuracy vs. latency:
   ```sql
   -- Dynamically boost recall to 99.5% for high-accuracy financial/legal queries:
   SET LOCAL hnsw.ef_search = 100;
   ```

#### The HNSW RAM-Resident Requirement:
Unlike relational B-Trees, which scan contiguous 8KB disk pages sequentially, **HNSW graph traversal performs non-contiguous random memory hops across thousands of nodes in high-dimensional space**.

If an HNSW index exceeds PostgreSQL `shared_buffers` and spills to NVMe disk, query latency collapses from **$3\text{ ms}$ to over $600\text{ ms}$**, degrading search performance below that of a simple flat scan!

#### Exact Memory Footprint Formula:
Calculate your server's RAM budget before deploying `pgvector` to production:

$$\text{Bytes Per Vector} \approx (D \times 4) + (2 \times m \times 8) + 32 \text{ bytes overhead}$$

For **1,000,000 OpenAI embeddings** ($D = 1536$ dimensions) with $m = 16$:
$$\text{Bytes Per Vector} = (1536 \times 4) + (32 \times 8) + 32 = 6,144 + 256 + 32 = \mathbf{6,432 \text{ bytes}}$$

$$\text{Total HNSW Index Size} = 1,000,000 \times 6,432 \text{ bytes} \approx \mathbf{6.43 \text{ GB of RAM}}$$

Ensure that `shared_buffers` plus Linux Page Cache can keep the entire 6.43 GB index **permanently pinned in physical RAM**.

## 7. Production Spring Boot Integration with Spring AI

```java
package com.backend.mastery.database.search;

import org.springframework.ai.embedding.EmbeddingModel;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Service;

import java.util.List;

@Service
public class SemanticSearchService {

    private final EmbeddingModel embeddingModel;
    private final JdbcTemplate jdbcTemplate;

    public SemanticSearchService(EmbeddingModel embeddingModel, JdbcTemplate jdbcTemplate) {
        this.embeddingModel = embeddingModel;
        this.jdbcTemplate = jdbcTemplate;
    }

    public List<SearchResult> searchProducts(String userPrompt, int limit) {
        // 1. Generate 1536-dimensional vector embedding for user query
        float[] queryVector = embeddingModel.embed(userPrompt);
        String vectorString = formatVectorForPostgres(queryVector);

        // 2. Perform Cosine Similarity Search using HNSW index
        String sql = """
            SELECT id, title, 1 - (embedding <=> ?::vector) AS score
            FROM product_embeddings
            ORDER BY embedding <=> ?::vector
            LIMIT ?
            """;

        return jdbcTemplate.query(
            sql,
            (rs, rowNum) -> new SearchResult(
                rs.getLong("id"),
                rs.getString("title"),
                rs.getDouble("score")
            ),
            vectorString, vectorString, limit
        );
    }

    private String formatVectorForPostgres(float[] vector) {
        StringBuilder sb = new StringBuilder("[");
        for (int i = 0; i < vector.length; i++) {
            sb.append(vector[i]);
            if (i < vector.length - 1) sb.append(",");
        }
        sb.append("]");
        return sb.toString();
    }

    public record SearchResult(Long id, String title, Double score) {}
}
```

## Search, CDC & Vector Fundamentals Interview Map

Search is not the same as lookup. CDC is not the same as dual-writing. Vector search is not the same as SQL filtering.

### 1. Lookup vs search

Lookup:

```sql
SELECT *
FROM products
WHERE id = 42;
```

Search:

```console
User types: "wireless noise canceling travel headphones"
```

Search needs tokenization, scoring, typo tolerance, language processing, and ranking.

### 2. Inverted index mental model

```mermaid
flowchart LR
    Term["headphones"] --> Docs["doc 7, doc 9, doc 42"]
    Term2["wireless"] --> Docs2["doc 9, doc 15, doc 42"]
    Query["wireless headphones"] --> Intersect["Intersect postings + score"]
```

A B-Tree answers ordered scalar lookup. An inverted index answers text relevance.

### 3. CDC vs application dual-write

Application dual-write:

```java
db.save(product);
search.index(product);
```

This can corrupt state when one write succeeds and the other fails.

CDC reads committed database changes from the WAL after the database has already decided truth.

### 4. Vector search basics

Embeddings turn meaning into numbers. Similar text has nearby vectors.

```sql
SELECT id, title
FROM product_embeddings
ORDER BY embedding <=> :queryEmbedding
LIMIT 10;
```

Vector search is approximate when using HNSW/IVFFlat indexes. You trade recall, memory, and latency.

## 8. Failure Modes & Edge Case Matrix

| Failure Mode | Component | Root Cause | Impact | Production Defense |
| :--- | :--- | :--- | :--- | :--- |
| **Silent Data Drift** | App Dual-Write | Network drop between DB commit and ES write | Search results out of sync with DB | Eliminate app dual-writes; use Debezium CDC from PostgreSQL WAL. |
| **Out-of-Order Overwrite** | Kafka Ingestion | Parallel consumer threads commit updates out of order | Stale record overwrites fresh record | Enforce external versioning in OpenSearch (`version_type=external_gte`). |
| **Search-After-Write Blindness** | OpenSearch Index | User queries before Lucene 1s refresh interval | User cannot find item just created | Return optimistic client state; pass `?refresh=wait_for` on critical admin writes. |
| **Replication Slot Disk Full** | PostgreSQL WAL | Debezium offline while primary continues writing | PG retains all WAL files; 100% disk full triggers database PANIC | Set `max_slot_wal_keep_size = 64GB` and alert when retained WAL > 10GB. |
| **HNSW OOM Eviction** | pgvector | Vector index outgrows PostgreSQL `shared_buffers` | Vector queries drop from 4ms to 600ms due to random flash thrashing | Calculate RAM using $(D \times 4 + 2m \times 8 + 32) \times N$ and keep graph pinned in memory. |

## 9. Senior Interview Questions & Active Recall

<AccordionGroup>
  <Accordion title="Why is writing to both PostgreSQL and Elasticsearch in application code considered an anti-pattern?">
    Application-level dual-writes lack atomic two-phase commit guarantees across heterogeneous databases. If the database transaction commits but the Elasticsearch write times out, data diverges permanently. If the Elasticsearch write succeeds but the database transaction rolls back, Elasticsearch stores phantom records. Furthermore, concurrent out-of-order network deliveries can cause older updates to overwrite newer ones.
  </Accordion>
  <Accordion title="How does Debezium CDC solve the dual-write problem?">
    Debezium attaches as a logical replication client to the PostgreSQL Write-Ahead Log (WAL). Because the WAL is the single, immutable, sequentially ordered source of truth for all committed transactions, Debezium extracts change events without application code intervention. It streams these events into Kafka with guaranteed ordering per partition key, enabling idempotent consumers to update Elasticsearch reliably.
  </Accordion>
  <Accordion title="What happens if a Debezium Kafka Connect worker crashes and stays offline for 48 hours?">
    PostgreSQL logical replication slots hold onto the `restart_lsn`. As long as the slot remains unconsumed, the PostgreSQL checkpointer is strictly forbidden from recycling or deleting WAL segments newer than `restart_lsn`. If write volume is high, the `pg_wal` directory will fill 100% of the physical disk, forcing PostgreSQL into an emergency panic shutdown. In production, we set `max_slot_wal_keep_size = 64GB` to automatically invalidate stale slots before disk exhaustion occurs, and monitor `pg_replication_slots` with alerts.
  </Accordion>
  <Accordion title="Why does an HNSW vector index require vastly more RAM than an IVFFlat index, and how do you calculate its memory footprint?">
    IVFFlat partitions vectors into inverted lists, needing only vector storage plus centroid pointers. In contrast, HNSW builds a multi-layer proximity graph where every vector maintains $m$ bidirectional pointers across multiple layers. Because graph traversal requires non-contiguous random memory hops, spilling from RAM to disk causes extreme $200\times$ latency degradation. Memory footprint is calculated as:
    $$\text{RAM} \approx (D \times 4 + 2m \times 8 + 32) \times N \text{ bytes}$$
    For 1M vectors at 1536 dimensions with $m=16$, the HNSW index requires ~6.43 GB of dedicated physical memory.
  </Accordion>
  <Accordion title="When should you use pgvector over a dedicated Elasticsearch cluster?">
    Use **`pgvector`** when you want semantic AI search tightly integrated with your relational queries (e.g., filtering products by tenant ID, price range, and user permissions in a single atomic SQL query) without the operational burden of managing a separate Elasticsearch cluster. Use **Elasticsearch** when you require high-throughput lexical full-text search, complex fuzzy matching, custom tokenizers, aggregations, and multi-terabyte search log scaling.
  </Accordion>
