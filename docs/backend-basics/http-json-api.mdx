# HTTP Internals, REST Architecture & JSON API Standards

Every modern backend system communicates over network protocols. Whether you are building internal microservices, external public APIs, or event webhooks, **HTTP and JSON form the universal lingua franca of backend engineering**.

A superficial understanding of HTTP (treating it merely as URLs and JSON payloads) leads to fragile systems that suffer from connection pool exhaustion, lack proper caching, leak security headers, and break client backwards-compatibility.

This guide provides an exhaustive, production-grade breakdown of the HTTP protocol stack, REST architectural constraints, RFC error standards, and JSON serialization mechanics.

---

## The Network Foundation: TCP and TLS Handshakes

Before a single byte of HTTP data is transmitted, the client and server must establish reliable transport and cryptographic trust.

```mermaid
sequenceDiagram
    autonumber
    actor Client as Client (Browser / Mobile / Service)
    participant Server as Backend Server (Nginx / Spring Boot)

    Note over Client,Server: Phase 1: TCP 3-Way Handshake (1 RTT)
    Client->>Server: SYN (Sequence Number = X)
    Server-->>Client: SYN-ACK (Ack = X+1, Seq = Y)
    Client->>Server: ACK (Ack = Y+1)

    Note over Client,Server: Phase 2: TLS 1.3 Cryptographic Handshake (1 RTT)
    Client->>Server: ClientHello + Key Share (Diffie-Hellman Public Key) + Supported Ciphers
    Server-->>Client: ServerHello + Key Share + Encrypted Certificate + Finished
    
    Note over Client,Server: Phase 3: Secure Encrypted HTTP Exchange (0.5 RTT)
    Client->>Server: HTTP Request (Encrypted with Derived Session Keys)
    Server-->>Client: HTTP Response (Encrypted)
```

### Handshake Latency Cost
1. **TCP 3-Way Handshake**: Takes 1 Round Trip Time (RTT).
2. **TLS 1.3 Handshake**: Takes 1 RTT (compared to TLS 1.2 which required 2 RTTs).
3. **Total Connection Overhead**: 2 full RTTs before application data can travel. Across a cross-country 60ms link, establishing a fresh connection costs **120ms** of latency before the backend even parses the request!

<Tip>
**Production Takeaway: Connection Keep-Alive**:
Always enable HTTP persistent connections (`Keep-Alive`). Reusing established TCP/TLS connections reduces request latency from 130ms to 10ms by eliminating redundant handshakes.
</Tip>

## Evolution of HTTP: 1.1 vs HTTP/2 vs HTTP/3 QUIC

Understanding the differences between HTTP versions explains why modern cloud gateways and CDNs optimize connection multiplexing:

```mermaid
graph TD
    subgraph HTTP/1.1
        H1["HTTP/1.1: Text-Based<br/>One request per TCP connection at a time<br/>Application Head-of-Line Blocking"]
    end
    subgraph HTTP/2
        H2["HTTP/2: Binary Framing<br/>Multiple streams multiplexed over 1 TCP connection<br/>TCP Head-of-Line Blocking on packet loss"]
    end
    subgraph HTTP/3
        H3["HTTP/3: UDP (QUIC Protocol)<br/>Independent streams over UDP<br/>Zero Head-of-Line Blocking + 0-RTT Reconnect"]
    end
    H1 -->|Multiplexing| H2
    H2 -->|Eliminate TCP HoL| H3
```

### Protocol Comparison Matrix

| Architectural Dimension | HTTP/1.1 | HTTP/2 | HTTP/3 (QUIC) |
| :--- | :--- | :--- | :--- |
| **Transport Layer** | TCP | TCP | UDP (via QUIC) |
| **Framing** | Plain text (ASCII) | Binary frames | Binary frames |
| **Multiplexing** | No (Sequential or Pipelined) | Yes (Multiplexed streams) | Yes (True independent streams) |
| **Head-of-Line (HoL) Blocking** | Severe (at HTTP application layer) | Eliminated at HTTP layer; persists at TCP layer | Completely eliminated across all layers |
| **Connection Handshake** | TCP (1 RTT) + TLS (1-2 RTT) | TCP (1 RTT) + TLS 1.3 (1 RTT) | QUIC (1 RTT combined transport + TLS 1.3) |
| **Header Compression** | None (Repeated raw headers) | HPACK (Indexed table) | QPACK (Out-of-order dynamic table) |
| **Connection Migration** | Impossible (IP/Port bound) | Impossible (IP/Port bound) | Seamless (Connection ID preserved across Wi-Fi/Cellular switches) |

## HTTP Anatomy: Requests and Responses

### The Wire Anatomy of an HTTP Request
HTTP/1.1 is human-readable on the wire. A raw request consists of three distinct blocks:

```http
POST /api/v1/orders HTTP/1.1
Host: api.store.com
User-Agent: iOS/17.4 PaymentClient/2.1
Authorization: Bearer eyJhbGciOiJIUzI1NiIsIn...
Content-Type: application/json
Content-Length: 54
Idempotency-Key: 9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d
Accept: application/json

{"productId":"prod_991","quantity":2,"unitPrice":49.99}
```

Read the request like a backend engineer, not like a copy-paste snippet:

| Line | What it physically means | What Spring/backend behavior depends on it |
| :--- | :--- | :--- |
| `POST /api/v1/orders HTTP/1.1` | The request line: method, path, and protocol version. | `POST` says this is a state-changing command. `/api/v1/orders` must match a route such as `@PostMapping("/api/v1/orders")`. |
| `Host: api.store.com` | The domain the client intended to reach. | Reverse proxies and API gateways use it to route many domains through the same IP address. |
| `User-Agent: iOS/17.4 PaymentClient/2.1` | Client software identity. | Useful for debugging rollout bugs, mobile version incompatibilities, and suspicious traffic. Never use it as a security proof because clients can forge it. |
| `Authorization: Bearer ...` | Access token proving caller identity, usually JWT or opaque token. | Spring Security reads this before the controller. If missing or invalid, the controller should not run. |
| `Content-Type: application/json` | The body format. | Spring selects Jackson to deserialize the body into a Java DTO. Wrong value can produce `415 Unsupported Media Type`. |
| `Content-Length: 54` | Number of body bytes that follow. | The server knows when the request body is complete. Wrong lengths can cause hanging reads or rejected requests. |
| `Idempotency-Key: ...` | Client-generated unique key for one business attempt. | Lets the backend safely handle retries without charging twice or creating duplicate orders. |
| `Accept: application/json` | The response format the client wants. | Spring content negotiation decides whether JSON is acceptable. |
| Empty line | Header/body delimiter. | HTTP parsers require this boundary. Everything after it is body bytes. |
| JSON body | Client intent. | The backend must validate it and load trusted price/state from the database. |

The dangerous part is the body:

```json
{"productId":"prod_991","quantity":2,"unitPrice":49.99}
```

Line by line:

- `productId` is client intent. The client is allowed to say which product it wants.
- `quantity` is also client intent, but it must be validated. `0`, `-1`, or `999999999` should fail before business logic reserves stock.
- `unitPrice` is suspicious. A production backend should not trust a price supplied by the client. The service should load the authoritative price from the database.

Better request shape:

```json
{"productId":"prod_991","quantity":2}
```

Then the service does this:

```console
Client says: productId=prod_991, quantity=2
Backend loads product prod_991 from database
Backend reads current price from trusted row
Backend checks inventory atomically
Backend creates order with server-calculated total
```

That is the difference between an API that merely receives JSON and an API that protects business rules.

```http
[Method] [Request-URI] [HTTP-Version] \r\n  <-- Request Line
[Header-Name]: [Header-Value] \r\n          <-- Request Headers
...
\r\n                                        <-- Empty Line (CRLF delimiter)
[Message Body Payload]                      <-- Optional Body
```

### The Wire Anatomy of an HTTP Response

```http
HTTP/1.1 201 Created
Date: Thu, 10 Sep 2026 15:30:00 GMT
Content-Type: application/json; charset=UTF-8
Content-Length: 82
Location: /api/v1/orders/ord_55219
ETag: W/"a8f12c-0912"
Cache-Control: private, no-cache

{"id":"ord_55219","status":"PENDING","totalAmount":99.98,"createdAt":"2026-09-10T15:30:00Z"}
```

Response line by line:

| Line | Meaning | Production reason |
| :--- | :--- | :--- |
| `HTTP/1.1 201 Created` | The request succeeded and created a resource. | Clients, gateways, logs, and tests can distinguish creation from normal `200 OK` reads. |
| `Date: ...` | Server response timestamp. | Useful for cache validation, clock debugging, and HTTP intermediaries. |
| `Content-Type: application/json; charset=UTF-8` | Body is JSON encoded as UTF-8. | Clients decode the body correctly. |
| `Content-Length: 82` | Body length in bytes. | Helps clients know when the response body is complete, especially on persistent connections. |
| `Location: /api/v1/orders/ord_55219` | Canonical URI for the new order. | A client can follow this URI to fetch the created resource. |
| `ETag: W/"a8f12c-0912"` | Version/hash-like validator for the representation. | Enables conditional requests and optimistic cache revalidation. |
| `Cache-Control: private, no-cache` | Browser may store privately but must revalidate before reuse. | Prevents shared proxies from caching user-specific order data. |
| JSON body | Public response contract. | Should expose only safe fields, not internal database columns or security-sensitive data. |

Body field explanation:

- `id` is server-generated. The client should not choose order IDs unless the API explicitly supports client-generated IDs.
- `status` tells the client the workflow state. `PENDING` means the order exists, but later payment or fulfillment steps may still happen.
- `totalAmount` should be calculated by the backend from trusted product price, discounts, tax rules, and quantity.
- `createdAt` is a server timestamp. It helps clients sort and audit without trusting device clocks.

### Controller Mapping For This Request

The HTTP request above usually maps to a Spring controller like this:

```java
@PostMapping("/api/v1/orders")
ResponseEntity<OrderResponse> createOrder(
        @RequestHeader("Idempotency-Key") String idempotencyKey,
        @AuthenticationPrincipal AuthenticatedUser user,
        @Valid @RequestBody CreateOrderRequest request) {
    OrderResponse response = orderService.createOrder(user.id(), idempotencyKey, request);
    URI location = URI.create("/api/v1/orders/" + response.id());
    return ResponseEntity.created(location).body(response);
}
```

Every line has a job:

- `@PostMapping("/api/v1/orders")` binds the HTTP method and path to this Java method. A `GET` to the same path should not accidentally create an order.
- `ResponseEntity<OrderResponse>` lets the method control status code, headers, and body instead of returning only JSON.
- `@RequestHeader("Idempotency-Key")` reads the retry-safety key from the HTTP headers. If a mobile client times out and retries, the service can detect the same business attempt.
- `@AuthenticationPrincipal AuthenticatedUser user` comes from Spring Security after token validation. This is safer than accepting `userId` in the JSON body.
- `@Valid @RequestBody CreateOrderRequest request` tells Spring to deserialize JSON into a DTO and validate its annotations before the service runs.
- `orderService.createOrder(...)` moves business logic out of the controller. The service should load trusted price, check stock, and write the order.
- `URI.create(...)` builds the resource URI for the `Location` header.
- `ResponseEntity.created(location).body(response)` returns `201 Created`, includes `Location`, and serializes `OrderResponse` as JSON.

Common beginner bug:

```java
@PostMapping("/api/v1/orders")
Order createOrder(@RequestBody Order order) {
    return orderRepository.save(order);
}
```

Why it is dangerous:

- The API accepts a database entity directly, so the client may set fields it should never control.
- There is no `@Valid`, so invalid data can reach the service or database.
- There is no authenticated principal, so ownership may come from an untrusted request field.
- There is no idempotency key, so retries can duplicate orders.
- Returning `Order` leaks persistence shape and can trigger lazy-loading problems during JSON serialization.

## Method Semantics: Safety, Idempotency & Cacheability

HTTP methods are strictly categorized by formal RFC 9110 architectural properties:

| Method | Primary Purpose | Safe? | Idempotent? | Cacheable? | Request Body? | Response Body? |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **GET** | Retrieve representation of resource | **Yes** | **Yes** | **Yes** | No | Yes |
| **HEAD** | Retrieve headers only (metadata check) | **Yes** | **Yes** | **Yes** | No | No |
| **OPTIONS** | Query supported methods / CORS preflight | **Yes** | **Yes** | No | No | Optional |
| **POST** | Create child resource or trigger processing | No | **No** | Only with explicit headers | Yes | Yes |
| **PUT** | Replace resource completely or create at URI | No | **Yes** | No | Yes | Yes |
| **PATCH** | Apply partial modifications to resource | No | **No** (RFC standard) | No | Yes | Yes |
| **DELETE** | Remove resource representation | No | **Yes** | No | Optional | Optional |

### The Critical Distinctions

#### 1. Safe vs Unsafe
An operation is **Safe** if it does not alter server state. Clients can call `GET` or `HEAD` repeatedly without fear of mutating business records, making them safe for web crawlers, browser prefetching, and CDN edge caching.

Bad unsafe `GET`:

```java
@GetMapping("/api/orders/{id}/cancel")
public OrderResponse cancel(@PathVariable Long id) {
    return orderService.cancel(id);
}
```

Why this is broken:

- `@GetMapping` tells browsers, crawlers, caches, and monitoring tools that this route is safe to call.
- The path says `cancel`, which changes business state.
- A browser prefetch, link scanner, or crawler could accidentally cancel orders.
- Observability also becomes confusing because a read-looking endpoint mutates data.

Correct shape:

```java
@PostMapping("/api/orders/{id}/cancellations")
public ResponseEntity<OrderResponse> cancel(@PathVariable Long id) {
    OrderResponse response = orderService.cancel(id);
    return ResponseEntity.ok(response);
}
```

Line by line:

- `@PostMapping` honestly declares a state-changing command.
- `/api/orders/{id}/cancellations` models cancellation as a sub-resource/action record instead of hiding a mutation behind `GET`.
- `orderService.cancel(id)` should enforce ownership, current order status, refund rules, and idempotency if retries are possible.

#### 2. Idempotent vs Non-Idempotent
An operation is **Idempotent** if making $N$ identical requests produces the exact same server side-effects as making 1 request:
$$f(f(x)) = f(x)$$

```http
# PUT is Idempotent: repeating 10 times leaves state identical
PUT /users/42 HTTP/1.1
{"name": "Alice"}

# POST is Non-Idempotent: repeating 10 times creates 10 separate charges!
POST /users/42/charges HTTP/1.1
{"amount": 100}
```

Think about a real mobile network:

```console
Time 1: Client sends POST /orders.
Time 2: Server creates the order and commits the database transaction.
Time 3: The response packet is lost on the network.
Time 4: Client sees timeout and retries the same POST.
Time 5: Server creates a second order unless idempotency protection exists.
```

That is why idempotency is not academic. It is how APIs survive retries.

Production retry-safe `POST`:

```sql
CREATE TABLE idempotency_keys (
    user_id BIGINT NOT NULL,
    idempotency_key TEXT NOT NULL,
    response_status INT NOT NULL,
    response_body JSONB NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, idempotency_key)
);
```

What each column does:

- `user_id` scopes the key to one authenticated caller. Two different users may generate the same random key without colliding.
- `idempotency_key` stores the client retry key.
- `response_status` stores the original HTTP status, such as `201`.
- `response_body` stores the original response so a retry can receive the same result.
- `created_at` lets a cleanup job expire old keys.
- `PRIMARY KEY (user_id, idempotency_key)` is the concurrency guard. Two simultaneous retries cannot both insert the same key.

Service shape:

```java
@Transactional
public OrderResponse createOrder(Long userId, String idempotencyKey, CreateOrderRequest request) {
    Optional<StoredResponse> existing = idempotencyRepository.find(userId, idempotencyKey);
    if (existing.isPresent()) {
        return existing.get().toOrderResponse();
    }

    Order order = orderFactory.createFromTrustedState(userId, request);
    orderRepository.save(order);

    OrderResponse response = OrderResponse.from(order);
    idempotencyRepository.save(userId, idempotencyKey, 201, response);
    return response;
}
```

Important line explanations:

- `@Transactional` keeps order creation and idempotency-key storage in one database transaction. If one succeeds and the other fails, retry behavior becomes inconsistent.
- `find(userId, idempotencyKey)` checks whether this exact business attempt already completed.
- `return existing.get().toOrderResponse()` replays the first result instead of performing the side effect again.
- `orderFactory.createFromTrustedState(...)` should load price and inventory from the database, not trust client values.
- `idempotencyRepository.save(...)` records the response before the transaction commits.

Production caveat: the simplified code above still needs duplicate-key handling around concurrent first requests. In a real implementation, the database `PRIMARY KEY` is the final authority.

#### 3. PUT vs PATCH
- **PUT**: Replaces the **entire resource**. Any field omitted in the request body is set to `null` or default values.
- **PATCH**: Modifies **only the specified fields**, leaving omitted attributes untouched.

Concrete example:

Existing resource:

```json
{
  "id": 42,
  "title": "Transactions",
  "content": "Old content",
  "tags": ["spring", "database"]
}
```

Full replacement with `PUT`:

```http
PUT /api/notes/42
Content-Type: application/json

{
  "title": "Transactions Deep Dive",
  "content": "New full content",
  "tags": []
}
```

After this request, `tags` becomes empty because the client sent the complete new representation.

Partial update with `PATCH`:

```http
PATCH /api/notes/42
Content-Type: application/json

{
  "title": "Transactions Deep Dive"
}
```

After this request, only `title` changes. `content` and `tags` stay as they were.

Failure case:

```console
Mobile app version 1 knows fields: title, content.
Backend version 2 adds field: tags.
Mobile app sends PUT with only title and content.
Backend treats missing tags as empty.
All tags disappear.
```

That is why `PUT` requires careful versioning and full-resource contracts. For mobile clients, `PATCH` is often safer when clients do not always know every server field.

## HTTP Status Codes: The RFC Contract

Status codes inform the client's network layer and application runtime how to handle the result:

```mermaid
graph LR
    S["Status Codes"] --> C1["1xx Informational<br/>(Protocol switching)"]
    S --> C2["2xx Success<br/>(Request understood and accepted)"]
    S --> C3["3xx Redirection<br/>(Further action needed to complete)"]
    S --> C4["4xx Client Error<br/>(Fault lies with caller)"]
    S --> C5["5xx Server Error<br/>(Fault lies with backend)"]
```

### Production Status Codes Breakdown

<Tabs>
  <Tab title="2xx Success">
    - **`200 OK`**: Standard success for `GET`, `PUT`, `PATCH`, or `DELETE` returning data.
    - **`201 Created`**: Resource created successfully via `POST`. **Must** include a `Location` header pointing to the new resource URL.
    - **`202 Accepted`**: Request accepted for asynchronous background processing (e.g., video transcoding, batch import). Status is not complete yet.
    - **`204 No Content`**: Request succeeded with zero response body (standard for successful `DELETE` or empty `PUT`).
  </Tab>
  <Tab title="3xx Redirection & Caching">
    - **`301 Moved Permanently`**: Target resource permanently assigned new URI. Browsers cache this redirect indefinitely.
    - **`302 Found / 307 Temporary Redirect`**: Temporary redirect. `307` guarantees that the HTTP method (e.g., `POST`) will not be mutated to `GET` during redirect.
    - **`304 Not Modified`**: Conditional request response (`If-None-Match`). Payload was not retransmitted because client cache is still valid.
  </Tab>
  <Tab title="4xx Client Errors">
    - **`400 Bad Request`**: Malformed syntax, invalid JSON, or schema validation failure.
    - **`401 Unauthorized`**: Authentication missing or token invalid/expired (misnamed; actually means *Unauthenticated*).
    - **`403 Forbidden`**: Authenticated caller lacks permissions / RBAC roles for this specific resource.
    - **`404 Not Found`**: Resource does not exist at this URI.
    - **`409 Conflict`**: Request conflicts with current server state (e.g., unique email already registered, optimistic lock version mismatch).
    - **`422 Unprocessable Content`**: Syntactically valid JSON, but semantic business rules failed (e.g., checkout with negative discount).
    - **`429 Too Many Requests`**: Client crossed rate limit threshold. Should return `Retry-After` header.
  </Tab>
  <Tab title="5xx Server Errors">
    - **`500 Internal Server Error`**: Unhandled exception, null pointer, or uncaught backend crash.
    - **`502 Bad Gateway`**: Upstream reverse proxy (Nginx/Gateway) received an invalid response from backend microservice.
    - **`503 Service Unavailable`**: Server temporarily overloaded or undergoing maintenance.
    - **`504 Gateway Timeout`**: Upstream service failed to respond within reverse proxy's socket timeout window.
  </Tab>
</Tabs>

### 1. HTTP Caching with ETags and 304 Not Modified
ETags (Entity Tags) eliminate redundant bandwidth consumption when querying resources that change infrequently:

## Standardized Error Handling: RFC 7807 & RFC 9457

In the past, backend teams created arbitrary error payloads:
```json
// ANTI-PATTERN: Inconsistent, custom error JSON
{"success": false, "err": "User not found", "code": 1042}
```

The Internet Engineering Task Force (IETF) standardized API error reporting in **RFC 7807** (updated in **RFC 9457** as `application/problem+json`).

### Standard Problem Details Structure

```json
{
  "type": "https://api.store.com/errors/insufficient-funds",
  "title": "Insufficient Funds",
  "status": 422,
  "detail": "Your account balance of $42.50 is insufficient for this $100.00 debit.",
  "instance": "/accounts/acc_9921/transfers/tx_551",
  "invalidParams": [
    {
      "name": "amount",
      "reason": "Must be less than or equal to current account balance"
    }
  ]
}
```

### Spring Boot 3 Native ProblemDetail Support

Spring Boot 3 introduces first-class support for RFC 7807 via `ProblemDetail` and `ResponseEntityExceptionHandler`:

```java
package com.example.demo.exception;

import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.net.URI;
import java.time.Instant;

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(InsufficientFundsException.class)
    public ProblemDetail handleInsufficientFunds(InsufficientFundsException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
                HttpStatus.UNPROCESSABLE_ENTITY, 
                ex.getMessage()
        );
        problem.setTitle("Insufficient Account Balance");
        problem.setType(URI.create("https://api.store.com/errors/insufficient-funds"));
        problem.setProperty("accountId", ex.getAccountId());
        problem.setProperty("currentBalance", ex.getCurrentBalance());
        problem.setProperty("attemptedDebit", ex.getAttemptedDebit());
        problem.setProperty("timestamp", Instant.now());
        return problem;
    }
}
```

## JSON Serialization Internals with Jackson

Spring Boot uses **Jackson** (`ObjectMapper`) to serialize Java POJOs into JSON strings and deserialize HTTP JSON payloads into Java objects.

```mermaid
graph LR
    subgraph Deserialization [HTTP Request -> Java Object]
        JIN["JSON Stream"] --> TOKEN["Jackson Tokenizer / Parser"]
        TOKEN --> REFL["Constructor / Setters / Field Reflection"]
        REFL --> POJO["Java Domain Record / DTO"]
    end
    subgraph Serialization [Java Object -> HTTP Response]
        POJO2["Java DTO"] --> GETTER["Getters & Field Inspection"]
        GETTER --> GEN["Jackson JsonGenerator"]
        GEN --> JOUT["JSON Response Stream"]
    end
```

### 1. Java 21 Records as Production DTOs
Records are immutable, thread-safe, and natively supported by Jackson 2.15+:

```java
package com.example.demo.dto;

import com.fasterxml.jackson.annotation.JsonProperty;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Positive;

import java.math.BigDecimal;

public record CreateOrderRequest(
    @NotBlank(message = "Customer ID is required")
    String customerId,

    @NotBlank(message = "Product ID is required")
    String productId,

    @Positive(message = "Quantity must be greater than zero")
    int quantity,

    @JsonProperty("unit_price") // Explicit JSON snake_case mapping
    BigDecimal unitPrice
) {}
```

### 2. Date/Time Serialization Best Practices
By default, older Jackson configurations serialized `java.time.Instant` and `LocalDateTime` into numeric epoch timestamp arrays `[2026, 9, 10, 15, 30]`. In modern backends, **always enforce ISO-8601 strings**:

```yaml
# application.yml
spring:
  jackson:
    serialization:
      write-dates-as-timestamps: false
    date-format: yyyy-MM-dd'T'HH:mm:ss.SSSXXX
    default-property-inclusion: non_null # Exclude null fields from JSON responses
```

### 3. Preventing Infinite Recursion in JPA Entities
When serializing bidirectional JPA entity relationships, Jackson will loop infinitely until an `OutOfMemoryError` or `StackOverflowError` crashes the JVM:

```mermaid
graph LR
    Order["Order Entity"] -->|getLines()| OrderLine["OrderLine Entity"]
    OrderLine -->|getOrder()| Order
    Order -.->|Infinite Loop!| OrderLine
```

```java
// RESOLUTION: Never serialize JPA entities directly to HTTP clients!
// Always map entities to decoupled DTO records before returning.
```

## Richardson Maturity Model

Leonard Richardson developed a model that measures the degree to which a web service embraces REST principles:

```mermaid
flowchart BT
    L0["Level 0: The Swamp of POX<br/>Single RPC endpoint (POST /api/service)"] --> L1["Level 1: Resources<br/>Distinct URIs (/orders/12, /users/4)"]
    L1 --> L2["Level 2: HTTP Verbs & Status Codes<br/>Proper GET, POST, PUT, DELETE & HTTP 201, 404"]
    L2 --> L3["Level 3: Hypermedia Controls (HATEOAS)<br/>Self-documenting discoverable links (_links)"]
```

## API Versioning Strategies

When API contracts inevitably evolve, breaking changes must not disrupt legacy mobile apps or external integrations:

| Strategy | Syntax Example | Pros | Cons |
| :--- | :--- | :--- | :--- |
| **URI Path** | `/api/v1/users` | Easiest for clients; clear routing in gateways; straightforward CDN caching | Pollutes URL namespace; forces URI changes on non-breaking updates |
| **Custom Header** | `X-API-Version: 2` | Clean, persistent URIs; separation of resource identity from contract version | Difficult to test in standard browsers; breaks URL bookmarking/sharing |
| **Accept Header (Content Negotiation)** | `Accept: application/vnd.store.v2+json` | Purest REST model; adheres to content negotiation standards | Steep client learning curve; complex proxy and cache configuration |

## Common API Anti-Patterns & Mistakes

<Warning>
### 1. The "Everything is 200 OK" Trap
Returning `HTTP 200 OK` with a body like `{"status": 500, "error": "NullPointerException"}` breaks API gateway circuit breakers, prevents monitoring tools from tracking error budgets (SLOs), and forces client code to parse every JSON response manually.
</Warning>

<Warning>
### 2. Verbs in URI Paths
Designing endpoints like `POST /api/createUser` or `GET /api/deleteOrder?id=12` completely violates REST resource orientation. Use nouns for resources and verbs for methods:
`POST /api/users` and `DELETE /api/orders/12`.
</Warning>

<Warning>
### 3. Exposing Sensitive Credentials in Query Parameters
Sending authentication tokens or passwords in URLs:
`GET /api/users?auth_token=secret123`
is a critical vulnerability. Query parameters are logged in plaintext across browser history, reverse proxy access logs, and CDN edge traces.
</Warning>

## Basic API Questions, Answered Deeply

An API is not just "a URL that returns JSON." It is a contract across a hostile network boundary.

### 1. What is a resource?

A resource is a thing your system can name consistently: a user, note, order, invoice, upload, payment, or shipment.

Good resource URLs use nouns:

```http
GET /api/notes/42
POST /api/orders
DELETE /api/orders/9001
```

Bad URLs smuggle actions into names:

```http
POST /api/createOrder
GET /api/deleteNote?id=42
```

**Senior answer:** "A resource URI should identify domain state. The HTTP method communicates the operation. This keeps routing, caching, authorization, metrics, and client behavior predictable."

### 2. Why does `POST` create but `PUT` replaces?

`POST` sends a command to a collection. The server decides the new resource identity.

```http
POST /api/notes
Content-Type: application/json

{"title":"Transactions","content":"Atomic boundaries"}
```

`PUT` replaces a known resource at a known URI. If the client omits a field, the server must define whether that means "clear it" or "reject incomplete representation."

```http
PUT /api/notes/42
Content-Type: application/json

{"title":"Transactions","content":"Updated full content"}
```

`PATCH` modifies only supplied fields.

```http
PATCH /api/notes/42
Content-Type: application/json

{"title":"New title only"}
```

**Common failure:** using `PATCH` semantics in a `PUT` endpoint. Mobile clients then accidentally erase fields during version mismatch.

### 3. Why must request DTOs be separate from entities?

Entities model database-persisted domain state. Request DTOs model client intent.

```mermaid
flowchart LR
    Json["Untrusted JSON"] --> RequestDto["CreateOrderRequest<br/>client intent"]
    RequestDto --> Service["OrderService<br/>loads trusted state"]
    Service --> Entity["Order Entity<br/>domain invariant"]
    Entity --> ResponseDto["OrderResponse<br/>public contract"]
```

Do not expose entities directly because:

- A request entity can allow mass assignment, such as setting `role = ADMIN`.
- A response entity can leak internal fields, such as `passwordHash`.
- Jackson can trigger lazy JPA loading during serialization.
- Bidirectional relationships can recurse until `StackOverflowError`.
- API contracts become tied to database table shape.

Production rule:

```java
public record CreateUserRequest(
    @Email String email,
    @Size(min = 12, max = 72) String password
) {}

public record UserResponse(
    Long id,
    String email
) {}
```

The request never includes `id`, `role`, `passwordHash`, `createdAt`, or `updatedAt` unless the use case truly allows the client to control them.

### 4. How do you choose HTTP status codes?

Use status codes to tell infrastructure and clients what happened without parsing custom strings.

| Situation | Status | Why |
| :--- | :--- | :--- |
| Resource created | `201 Created` | Include `Location` header |
| Valid deletion with no body | `204 No Content` | Nothing else to render |
| Invalid JSON or field validation | `400 Bad Request` | Client sent malformed input |
| Missing/invalid login token | `401 Unauthorized` | Caller has not authenticated |
| Authenticated but not allowed | `403 Forbidden` | Identity is known but forbidden |
| Missing resource or hidden foreign resource | `404 Not Found` | Avoid leaking existence |
| Duplicate idempotency key conflict | `409 Conflict` | Current state conflicts with request |
| Rate limit exceeded | `429 Too Many Requests` | Client should slow down |
| Downstream dependency unavailable | `503 Service Unavailable` | Retry later may work |

**Senior answer:** "Status codes are part of the distributed contract. Gateways, retries, circuit breakers, SLOs, logs, and clients all depend on them. Returning `200` for errors destroys observability and pushes protocol logic into every caller."

### 5. What is idempotency in APIs?

An operation is idempotent when repeating it produces the same final server state.

`GET /notes/42` is naturally idempotent. `DELETE /notes/42` is idempotent because after one or ten deletes, the final state is "deleted."

`POST /orders` is not naturally idempotent. If the mobile client times out and retries, the server may create two orders.

Use an idempotency key:

```http
POST /api/orders
Idempotency-Key: 8d2fd4a8-f9c7-48b6-97f1-c5d2e2f1a111
Content-Type: application/json

{"productId":42,"quantity":1}
```

Database proof:

```sql
CREATE UNIQUE INDEX uq_orders_user_idempotency_key
ON orders(user_id, idempotency_key);
```

**Senior answer:** "Retries are guaranteed in real networks. Idempotency turns ambiguous client retries into deterministic server behavior by storing request identity and replaying the original result instead of repeating the side effect."

## Active Recall & Interview Mastery

<AccordionGroup>
  <Accordion title="1. Explain the difference between HTTP Safe and Idempotent methods.">
    A method is **Safe** if it does not modify server state (e.g., `GET`, `HEAD`, `OPTIONS`). A method is **Idempotent** if invoking it once produces the exact same server side-effect as invoking it multiple consecutive times with the same parameters (e.g., `PUT`, `DELETE`, `GET`). All safe methods are idempotent, but not all idempotent methods are safe (`DELETE` mutates state by removing a resource, but executing `DELETE /orders/5` multiple times leaves the system in the same final deleted state).
  </Accordion>

  <Accordion title="2. How does HTTP/2 eliminate Head-of-Line blocking, and why can it still suffer from it under packet loss?">
    HTTP/1.1 suffers from application-level Head-of-Line blocking because requests on a TCP connection must be processed sequentially. HTTP/2 introduces binary framing and stream multiplexing, allowing multiple interleaved requests and responses over a single TCP connection. However, because HTTP/2 still relies on a single underlying TCP connection, if a single TCP packet drops on a congested network, the OS TCP stack pauses all streams until the missing packet is retransmitted. HTTP/3 solves this by replacing TCP with UDP (QUIC), isolating packet loss to individual streams.
  </Accordion>

  <Accordion title="3. What is the difference between PUT and PATCH in RESTful API design?">
    `PUT` is a full replacement: the client sends a complete representation of the resource. Any attribute omitted from the request body is set to `null` or default values. `PATCH` is a partial update: the client sends only the fields that need modification, and the backend leaves all other existing entity attributes intact.
  </Accordion>

  <Accordion title="4. How does the ETag and If-None-Match conditional request flow save server bandwidth?">
    When a server sends a response, it calculates a hash of the content and returns it in the `ETag` header. On subsequent requests for that resource, the client sends that hash back in the `If-None-Match` header. If the server's current resource hash matches the client's ETag, the server returns an empty `HTTP 304 Not Modified` header response without serializing or transmitting the full JSON payload over the network.
  </Accordion>

  <Accordion title="5. What is RFC 9457 / RFC 7807 Problem Details, and why is it preferred over custom error JSON?">
    RFC 9457 defines a standardized HTTP error payload format (`application/problem+json`) consisting of `type` (URI reference), `title` (human-readable summary), `status` (HTTP status code), `detail` (specific error explanation), and `instance` (URI where error occurred). It provides a uniform error schema across microservices, enabling generic error-handling clients, standardized logging, and frontend error formatting without custom per-endpoint parsing logic.
  </Accordion>
</AccordionGroup>
