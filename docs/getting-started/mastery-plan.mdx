# Mastery Plan

Track what you can do after the tutorial is closed. Page count, study streaks, and familiarity with terminology do not demonstrate the same skill as building and debugging.

Follow the [roadmap](/getting-started/backend-roadmap). Use the [assessments](/getting-started/mastery-assessments) after each stage, and keep the evidence in your own learning repository.

## Four levels of evidence

| Level | What you can demonstrate | Evidence |
| --- | --- | --- |
| Recognize | Explain a term and identify it in code | A short explanation and a concrete example |
| Build with guidance | Follow a walkthrough and get the expected behavior | Source, run command, and results |
| Build independently | Implement a changed requirement without the walkthrough | A new implementation and behavior tests |
| Diagnose and judge | Reproduce a failure, fix its cause, and defend a tradeoff | Failing/passing test, diagnostic notes, and alternatives |

Advance to the next stage when its required outcomes work independently. Keep deeper topics open for later practice. You can be independent at REST validation while still learning database isolation.

## Keep a small evidence portfolio

For each feature, save one record with these fields. A Markdown file in your application repository is sufficient.

| Field | Example: Todo title validation |
| --- | --- |
| Requirement | Titles must contain visible text and be at most 120 characters. |
| Prediction | A request containing only spaces returns 400 and creates no row. |
| Reproduction | Exact request, application version, database setup, and test command. |
| Result | Response body plus the database assertion after the request. |
| Failure found | Update initially accepted blank titles even though create rejected them. |
| Fix | Apply the same boundary rule to both operations. |
| Regression proof | Tests fail on the old implementation and pass after the fix. |
| Independent variation | Add a 120/121-character boundary test without the walkthrough. |
| Open question | Decide how the product should count Unicode characters before supporting this requirement across clients. |

Record actual results. A planned test remains planned until you run it. If your environment blocks a test, record the blocker and the last verified step.

## Repeat skills with a changed problem

Revisit a skill in a later session and again after another project. These are practice suggestions, not deadlines.

| First exercise | Later transfer exercise |
| --- | --- |
| Reject invalid task input | Reject invalid note updates and prove no row changed |
| Find an item in a Java map | Distinguish missing database rows from unauthorized access |
| Roll back a two-row change | Prevent negative inventory under concurrent requests |
| Retry a failed local operation | Handle a repeated event without repeating a business action |
| Measure one endpoint | Explain why its load-test result does not predict a different workload |

Before opening old notes, predict the design and the failure cases. Compare your result with the earlier evidence afterward.

## Explain One Line Until It Becomes A Skill

When a concept feels familiar but not usable, pick one line and expand it:

```java
@Transactional
public void transfer(AccountId from, AccountId to, Money amount) {
```

Minimum explanation:

- `@Transactional` means Spring opens a database transaction through a proxy before the method body runs.
- The transaction binds one database connection to the current thread.
- Both debit and credit must commit together or roll back together.
- A runtime exception escaping the method triggers rollback by default.
- A checked exception does not roll back by default unless configured.
- Calling this method through `this.transfer(...)` from the same class bypasses the proxy and can skip the transaction.

Evidence task:

```console
Write a test where debit succeeds and credit throws.
Verify both account balances remain unchanged.
Then remove @Transactional and prove the test catches partial state.
```

This is the standard for every page: explanation becomes mastery only when a failure proves why the line exists.

## Build a sequence, then maintain something

The core sequence is plain Java → [Todo](/projects/todo-api-full-build) → [Notes](/projects/notes-api-full-build) → [Deployment](/projects/deployment-lab) → [Incident Debugging](/projects/incident-debugging-lab). Each step depends on the earlier behavior working.

Use [Blog](/projects/blog-api-full-build) for relationships and roles. Use [E-commerce](/projects/ecommerce-full-build), [Rate Limiter](/projects/rate-limiter-full-build), and [Notification Worker](/projects/notification-worker-full-build) for concurrency and distributed failure practice after their prerequisites.

Keep one service alive across several changes. Add a feature without breaking existing clients. Migrate data that already exists. Diagnose a report written by another person. Remove an unnecessary component and explain the tradeoff. This develops judgment that isolated walkthroughs cannot supply.

## Review your progress

At the end of a study cycle, answer these questions using links to your evidence:

- Which behavior can I now build independently?
- Which bug did I reproduce and prevent with a test?
- Which assumption did the result disprove?
- Which requirement would change my design?
- What is the next smallest exercise that closes a specific gap?

Choose the next exercise from the failed assessment criterion. If the missing skill is SQL rollback, practice a two-statement transaction; adding Kafka will not close that gap.
