## Technical corrections

| Area | Correction | Why it matters |
| --- | --- | --- |
| [Refresh tokens](/production/security-jwt) | Serialize by family; commit revocation before returning an error | An unchecked exception could undo revocation |
| [Authorization](/spring-boot/spring-security-production) | Check stored ownership; separate cookie CSRF and bearer APIs | A caller-supplied owner ID is not proof |
| [Kafka](/advanced/message-queues) | Commit before acknowledgment; distinguish blocking retries from retry topics | Avoid losing work at the acknowledgment boundary |
| [Schema changes](/database/schema-change-mastery) | Use actual Flyway script configuration | A SQL comment does not configure execution |
| [Pagination](/database/database-performance-mastery) | Matching indexes and qualified keyset cost | Keyset access is not universally constant time |
| [Caching](/production/caching) | Explain stale refill races | Deleting a key does not establish strong consistency |
| [Quorums](/system-design/consistency-failures) | State overlap assumptions | Overlap alone does not establish linearizability |
| [Java](/java/java-core) | Shallow record immutability and benchmark requirements | Measurements are not language guarantees |
| [E-commerce](/projects/ecommerce-full-build) | Remove hardcoded webhook parsing and incorrect verification; let failed transactions roll back | Payment examples must expose integration gaps |

These corrections improve explanations. Most advanced excerpts still need complete integration projects before their behavior is verified here.

## Remaining priorities

0. **Explanation-density sweep.** Continue converting every chapter from definition-heavy reference notes into example-heavy lessons. Each major topic should show the problem, a realistic example, important-line explanations, a failure mode, the fix, and a proof step.
1. **PostgreSQL Todo continuation.** Add Testcontainers tests for migrations, persistence, rollback, and concurrency. Prove restore into a fresh database.
2. **Complete authenticated Notes.** Supply missing auth integration. Test decoder failures, ownership, CSRF, rotation races, and committed family revocation.
3. **Executable advanced capstones.** Give Blog, E-commerce, URL Shortener, Rate Limiter, and Notification Worker complete source, pinned builds, and CI. Separate simulations from provider integration.
4. **Consistency across chapters.** Repeated explanations still risk drift. Link summaries to canonical chapters and continue reviewing numerical claims and API assumptions.
5. **Beginner usability.** Test setup with a new learner. Record missing steps and unfamiliar terms, then add focused exercises where needed.
6. **Operational proof.** Turn recovery and load exercises into repeatable fixtures with saved results. A runbook is not a completed drill.

## Stronger claims need stronger evidence

Every core project should build from a fresh checkout, pass tests against real dependencies, and include an independent extension. A new learner should complete setup without undocumented help. Advanced claims need primary sources and reproducible experiments.

Until that evidence exists, use this as an improving course and reference. Judge progress by what you can build, diagnose, and explain using the [assessment gates](/getting-started/mastery-assessments).
