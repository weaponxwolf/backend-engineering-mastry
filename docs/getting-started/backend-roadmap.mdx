# Backend Engineering Roadmap

Start with a small program. Turn it into an API. Store its data. Protect access. Then learn to operate it when things fail.

The sidebar groups chapters by subject. **This roadmap gives the order in which to learn them.** You will revisit several chapters as your projects grow. You do not need to understand every section on the first visit.

<Note>
Completing a reading list does not establish a job level. Senior and staff work also requires experience with real users, maintenance, collaboration, and decisions under uncertainty. This guide gives you a path to practice those skills and record evidence.
</Note>

## Choose your entry point

| You can already do this independently | Start here |
| --- | --- |
| I have never compiled a program | Stage 0: tools and first program |
| I can use variables, conditions, loops, methods, and lists | Stage 1: Java and HTTP |
| I can build a Java program and explain an HTTP request | Stage 2: first Spring API |
| I can build and test an API that stores data | Stage 3: persistent, secure service |
| I can protect data and reproduce concurrency bugs | Stage 4: operating a service |
| I can restore a service and diagnose failures | Stage 5: distributed work |

Use the [mastery assessments](/getting-started/mastery-assessments) to check your entry point. If you need a solution open beside you, use the preceding stage for practice.

## Stage 0: tools and first program

**Build:** a Java program that calculates an order total and rejects invalid quantities.

1. Complete [Your First Java Program](/getting-started/first-program).
2. Run the checked-in `examples/java-foundations` lab from the repository root.
3. Change one business rule, predict the result, and run the program again.

**Learn now:** files and folders, terminal commands, source code, compilation, variables, methods, conditions, and reading an error message.

**Return later:** bytecode inspection, garbage collector algorithms, CPU cache behavior, and virtual threads. They become useful when you have a running program to investigate.

**Pass evidence:** source file, successful command output, one invalid-input example, and an explanation of the rule. Use [assessment 0](/getting-started/mastery-assessments#assessment-0-change-a-java-business-rule).

**Deep example:** do not only say "the program validates quantity." Explain the path:

```console
Input value -> method parameter -> if condition -> exception or multiplication -> printed result
```

Then prove both branches:

- `quantity = 3` reaches multiplication and prints `7500`.
- `quantity = 0` reaches the exception and never prints an order total.

This is the same mental model as an API later:

```console
HTTP JSON -> request DTO -> validation -> service rule -> database write or error response
```

## Stage 1: Java and HTTP foundations

**Build:** an in-memory task list in plain Java. Explain how a client would create and read one task over HTTP.

1. Practice objects and methods in [OOP](/java/oop), then lists, maps, and error handling in [Collections and Exceptions](/java/collections-exceptions).
2. Use [Java Core](/java/java-core) to explain the behavior of code you have run. Start with values, references, strings, and records. Revisit runtime internals later.
3. Read the request examples in [HTTP and JSON](/backend-basics/http-json-api). Identify method, path, headers, body, and response status.
4. Use [What Is Backend?](/backend-basics/what-is-backend) and [Client-Server](/backend-basics/client-server) to trace client → server → data → response. Leave the cloud and socket internals for a second pass.

**Learn now:** create/read/update/delete operations, missing items, duplicate identifiers, JSON, and HTTP success/error responses. An identifier is a value used to find a particular item.

**Pass evidence:** the Java foundations lab passes; you can add a new case and describe a request and response without framework annotations. Use [assessment 1](/getting-started/mastery-assessments#assessment-1-explain-a-request-and-find-a-failure).

**Deep example:** when you describe `POST /api/tasks`, include every boundary:

```http
POST /api/tasks HTTP/1.1
Content-Type: application/json

{"title":"Learn maps"}
```

- `POST` means create or trigger a state-changing command.
- `/api/tasks` names the collection.
- `Content-Type` tells the server how to parse the body.
- The JSON title is untrusted input.
- The response status should prove whether creation happened, failed validation, or hit a duplicate ID.

## Stage 2: build your first Spring API

**Prerequisites:** stages 0–1. Start SQL before adding JPA, the interface used here to map Java objects to database rows.

**Build:** [Todo API](/projects/todo-api-full-build), one endpoint at a time. Use the [project specification](/projects/todo-api) as the behavior contract.

1. Learn constructor injection in [Dependency Injection](/spring-boot/dependency-injection) and the request flow in [REST APIs](/spring-boot/rest-api).
2. Learn configuration values in [Configuration and Profiles](/spring-boot/config-profiles). Begin with one application and one local profile.
3. Read `CREATE TABLE`, `INSERT`, `SELECT`, `UPDATE`, and `DELETE` in [SQL Basics](/database/sql-basics), then the entity/repository examples in [JPA and Hibernate](/spring-boot/jpa-hibernate).
4. Add [Validation and Errors](/spring-boot/validation-errors) and start [Testing](/production/testing) while you build the first endpoint.
5. Use [Project Structure](/spring-boot/project-structure) to keep responsibilities understandable as the app grows.

**Return later:** hexagonal architecture, advanced query tuning, streaming responses, and distributed deployment. A single working request path is the first target.

**Pass evidence:** create, read, and update tests; a blank title is rejected; an unknown ID returns the documented error; the application starts from a clean checkout. Use [assessment 2](/getting-started/mastery-assessments#assessment-2-build-and-test-a-todo-api).

**Deep example:** for one endpoint, trace the full line:

```console
curl request -> controller annotation -> request DTO -> service method -> repository call -> database row -> response DTO -> status code
```

If you cannot point to the file and test for each arrow, you have read the topic but not mastered the path.

## Stage 3: persistent data and secure access

**Build:** [Notes API](/projects/notes-api-full-build). Keep the Todo project as a small regression exercise.

1. Model ownership with [Relationships and Joins](/database/relationships-joins). Learn constraints and transactions in [Indexes and Transactions](/database/indexes-transactions).
2. Manage schema changes with [Query Design and Migrations](/database/query-design-migrations). A migration is a versioned change to the database schema.
3. Study [Transaction Boundaries](/spring-boot/transactions), then [Security Architecture](/spring-boot/spring-security-deep) and [Production Security](/spring-boot/spring-security-production).
4. Test against PostgreSQL with [Testcontainers](/production/testcontainers). Test authentication and ownership separately. A valid login does not grant access to another user's data.
5. Use [Locking and Isolation](/database/locking-isolation) to investigate one concurrent update, then study [Schema Changes](/database/schema-change-mastery) before changing a populated table.

**Pass evidence:** data survives application restart; migrations initialize a fresh database; two different users cannot read or change each other's notes; rollback leaves no partial business operation. Use [assessment 3](/getting-started/mastery-assessments#assessment-3-protect-data-and-ownership).

**Extension:** build [Blog API](/projects/blog-api-full-build) to practice relationships, roles, and pagination. Add only one of those concerns at a time.

## Stage 4: operate and diagnose one service

**Build:** package your Notes or Blog API and complete the [Deployment Lab](/projects/deployment-lab).

1. Learn the container basics in [Docker and Kubernetes](/advanced/docker-kubernetes). Run one service and PostgreSQL locally before learning Kubernetes.
2. Add [Logging and Monitoring](/production/logging-monitoring), then [Observability](/production/observability). Trace one failed request from its response to the database call.
3. Measure a slow endpoint using [Database Performance](/database/database-performance-mastery) and [JVM Performance](/java/jvm-performance-tuning). Write down the workload, results, and limits before tuning.
4. Practice deployment and rollback in [CI/CD](/production/deployment-ci-cd).
5. Complete a local restore exercise and one [Incident Debugging Lab](/projects/incident-debugging-lab) scenario using [Incident Response](/production/incident-response).

**Pass evidence:** fresh-environment run instructions, a checked backup/restore, a failed-dependency test, and an incident report with a regression test. Use [assessment 4](/getting-started/mastery-assessments#assessment-4-operate-and-recover-a-service).

## Stage 5: distributed work and concurrency

**Prerequisites:** a service you can test, observe, and recover. Add another component only when you can name the problem it solves.

1. Revisit [Java Concurrency](/java/concurrency-jvm) and database locking through a stock-reservation exercise in [E-commerce](/projects/ecommerce-full-build).
2. Learn [Caching](/production/caching) and build a [Rate Limiter](/projects/rate-limiter-full-build). Test behavior when Redis is unavailable.
3. Learn [Message Queues](/advanced/message-queues) and build a [Notification Worker](/projects/notification-worker-full-build). An acknowledgment tells the broker that processing reached the intended boundary; test that boundary under failure.
4. Study [Resilience Patterns](/advanced/resilience-patterns) and [Consistency and Failures](/system-design/consistency-failures) using timeouts, duplicate events, and partial failures from your project.
5. Compare [Microservices](/advanced/microservices) with [Migration from a Monolith](/advanced/microservices-from-monolith). Write down the operational and data costs before splitting your application.

**Pass evidence:** repeated requests/events do not repeat a protected business action; concurrent requests preserve inventory; a dependency outage has a documented, tested outcome. Use [assessment 5](/getting-started/mastery-assessments#assessment-5-handle-concurrency-and-repeated-delivery).

## Stage 6: design with measured tradeoffs

**Build:** a design proposal, a prototype of its riskiest assumption, and an explanation of what the measurements do and do not prove.

1. Use [System Design Fundamentals](/system-design/fundamentals) to establish requirements, then [Capacity Estimation](/system-design/capacity-estimation) to quantify them.
2. Design the [URL Shortener](/system-design/url-shortener) before comparing it with the [build guide](/projects/url-shortener-full-build).
3. Choose a second problem: [Notification System](/system-design/notification-system), [Financial Ledger](/system-design/financial-ledger), or [Search Autocomplete](/system-design/search-autocomplete).
4. Study [Consensus and Fencing](/system-design/distributed-locks-consensus), [Sharding](/database/sharding-partitioning), and [Multi-Region Recovery](/system-design/multi-region-disaster-recovery) when your chosen requirements create those problems.
5. Defend a decision and adapt it to changed requirements using the [Interview Playbook](/interview/senior-interview-playbook).

**Pass evidence:** two alternatives, numbers with units and assumptions, failure behavior, a migration/rollback plan, and a measured prototype. Use [assessment 6](/getting-started/mastery-assessments#assessment-6-defend-a-system-design).

## Continue after the core path

Specialize through [Batch and Scheduling](/advanced/distributed-batch-scheduling), [Real-Time Systems](/advanced/realtime-websockets), [Search and CDC](/database/search-indexing-cdc), or [Reactive and Virtual Threads](/java/reactive-vs-virtual-threads) when you have a project that needs them.

Keep one service working as you make changes over several weeks. Ask someone else to run it, report a bug, and review a design. Use the [Mastery Plan](/getting-started/mastery-plan) to track what you can reproduce after the tutorial is closed.
