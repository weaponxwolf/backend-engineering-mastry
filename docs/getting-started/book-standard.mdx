# Book Replacement Standard

This guide should not be a collection of small notes.

Every serious topic must teach enough that a learner can build, debug, explain, and defend the idea in an interview.

## Evidence Before Labels

State prerequisites and versions. Identify whether code is a complete runnable lab, a project walkthrough, an excerpt, or an intentional failure. A runnable claim requires checked-in files and a successful fresh-checkout build/test command. MDX validation alone never verifies Java or SQL.

Start with a small example, then explain why it works. Add an independent variation and a reviewable expected result. Use the [mastery assessments](/getting-started/mastery-assessments) for larger gates. Avoid universal performance numbers and guarantees unless their assumptions and evidence are supplied.

## Chapter Standard

Every major chapter should include:

- Mental model
- Real backend use case
- Working code shape
- Request and response examples
- Database model when needed
- Failure cases
- Common mistakes
- Debug checklist
- Tests
- Production notes
- Interview answers
- Practice tasks
- Done checklist

If a page only defines words, it is not a mastery chapter.

## Explanation Density Standard

Every page must assume the learner is reading slowly and wants to understand the machinery behind each line.

Do not write:

```console
@Transactional starts a transaction.
```

Write the full chain:

```console
@Transactional tells Spring to call this method through a proxy.
The proxy asks PlatformTransactionManager for a database connection.
That connection is bound to the current thread while the method runs.
Hibernate uses the same connection when repositories execute SQL.
If an unchecked exception escapes the method, Spring rolls the transaction back.
If the method calls a slow payment API before returning, the connection stays occupied and the pool can run out.
```

The required depth is:

- **Definition**: What the term means in simple English.
- **Reason**: Why the term or tool exists.
- **Mechanism**: What happens in memory, on the network, inside Spring, inside PostgreSQL, or inside the JVM.
- **Example**: A realistic Java, SQL, HTTP, YAML, Docker, or Kubernetes example.
- **Line-by-line explanation**: Explain every important annotation, method call, clause, property, header, and field.
- **Failure mode**: Show the beginner mistake and the production symptom.
- **Fix**: Show the corrected code or architecture.
- **Proof**: Show how to test, log, query, or observe that the fix works.
- **Interview phrasing**: Show how to explain it clearly under pressure.

Short definitions are allowed only as labels inside a larger explanation. They are never enough by themselves.

## Knowledge Levels

Use four levels for every topic.

```console
Level 1  I know the definition
Level 2  I can write a small example
Level 3  I can use it in a real project
Level 4  I can debug, scale, secure, and explain tradeoffs
```

This guide should aim for level 4.

## What Mastery Means

Mastery does not mean knowing every API by memory.

Mastery means:

- You know what problem the tool solves
- You know when to use it
- You know when not to use it
- You can build with it without copying blindly
- You can debug common failures
- You understand tradeoffs
- You can explain it simply

## Required Capstones

A learner should complete these before claiming backend mastery:

```console
Todo API
Notes API with auth
Blog API with roles and comments
E-commerce backend
Notification system
URL shortener
Rate limiter
Production deployment
Incident debugging exercise
```

## Required Proof

For each capstone, the learner should have:

- Git repository
- README
- Database migrations
- Tests
- Dockerfile
- Local run instructions
- Error response format
- Security rules
- Production checklist

## Anti-Pattern

Bad learning:

```console
Read topic
Feel familiar
Move on
```

Good learning:

```console
Read topic
Build feature
Break feature
Fix bug
Write test
Explain tradeoff
Refactor code
Deploy or simulate production
```

## Rule

If the docs do not make you build and debug, they are not enough.
