# How To Use This Guide

Your first target is a program you can run, change, and explain. Start with [Your First Java Program](/getting-started/first-program), then follow the [Backend Roadmap](/getting-started/backend-roadmap).

If you already write Java, use the [mastery assessments](/getting-started/mastery-assessments) to find the first skill you cannot demonstrate independently. Start there.

## Reading the website and building an application

This repository contains the documentation site and executable examples under `examples/`. The other chapter examples describe applications you build in your own project directories.

`npm run dev` starts the documentation website. It does not start a Spring application. `npm run check` checks documentation quality; application behavior needs its own build and tests.

Before using a code example, identify its scope:

| Example type | How to use it |
| --- | --- |
| Runnable lab | Use the checked-in source and its exact run/test commands. |
| Project walkthrough | Follow its setup and assemble files in your own application. Confirm required configuration and dependencies. |
| Focused snippet | Apply the idea inside a project that supplies the surrounding classes and configuration. |
| Failure example | Predict the failure and reproduce it locally before applying the fix. |

A chapter title such as “full build” is not proof that every code block compiles together. Check the [curriculum audit](/getting-started/curriculum-audit) for known limitations and verification status.

## Use each chapter in two passes

On the first pass, find the problem, run the smallest example, and complete one exercise. Write down unfamiliar terms that block the exercise. Look up those terms immediately.

On the second pass, investigate internals, production failures, and tradeoffs using a working project. For example, learn to store a Todo before studying PostgreSQL page layout. Learn to call a method before inspecting generated bytecode.

If a chapter assumes knowledge you do not yet have, return to its stage in the roadmap. Reordering practice is part of learning; struggling with an unexplained prerequisite is not an assessment of your ability.

## A useful study session

Choose a small behavior, such as “reject a blank title.” Finish one loop:

1. **Predict:** write the expected output or HTTP response before running the code.
2. **Build:** implement the smallest change that produces that behavior.
3. **Break:** try a boundary case, missing data, or a failed dependency.
4. **Test:** add an assertion that would catch the failure you just found.
5. **Explain:** describe the cause and the fix without reading the chapter.
6. **Record:** save the command, result, and one remaining uncertainty.

For a short session, do one behavior. For a longer session, add a second test and review yesterday's change. A fixed daily schedule is optional; a runnable result is the useful unit of progress.

## Use help without hiding gaps

Use reference documentation for syntax and APIs. When using an assistant, ask for a hint, a failing case, or a review of your explanation. If it supplies the solution, mark that attempt as guided practice.

Then close the solution and solve a changed version. For example, after implementing task creation, implement title updates with the same validation rules. The second attempt reveals whether you can transfer the idea.

## When you get stuck

| Symptom | Next action |
| --- | --- |
| A command is missing | Check tool installation, terminal restart, and the directory named by the instructions. |
| Java cannot compile | Read the first compiler error, inspect that line, and fix one issue at a time. |
| The app starts but a request fails | Save method, URL, body, response status, and the matching application log. |
| A test passes but behavior looks wrong | Check what it actually asserts. Add an observable case that should fail. |
| The example assumes unknown classes | Locate the setup or record the missing piece; do not treat a snippet as a standalone program. |
| You understand the prose but cannot build | Return to a smaller exercise and change one input or rule. |

Keep your own error log. Record what you expected, what happened, how you investigated, and what fixed it. Reproduce a previous failure without reading your notes during later reviews.
